# reeve Builder Programme: The Design (amended after the 2026-08-21 audit)

**Status**: approved direction; implementation gated by P0 closure (audit 2026-08-21).

This is the design document for the builder programme, revised three times: once after 29 adversarial findings and the founder's gate revision of 2026-08-21 (Appendix A), once after the independent audit of the same day (Appendix B), and once more after three independent verifications of the amended text found 22 contradictions, each resolved by a lead ruling of 2026-08-21 and written into the section it belongs to (the mechanism changes are also recorded in Appendix B). The audit's nine P0 items, its P1 items, and its DX list were ruled on by the lead on 2026-08-21; every ruling is encoded below as design text in the section it belongs to. A fresh reader of any section sees one mechanism. **Which PRs are gated**: the P0 closure stages of §14 (S0 design freeze and FIELDS, S1 guardian-shared worker hardening, S2 hub core with the guardian-shared scheduler) are themselves PRs and may begin now, because none of them turns on a capability switch or performs an external effect. Every PR from S3 onward (the first one that can dispatch a worker under a switch) is authorized only after S0 through S2 have landed with the evidence each stage names.

**Settled requirements honored, not re-litigated**: Architecture A (per-task phase state machine in the existing daemon family, phases are bounded `claude` CLI workers through the existing supervisor, fan-out only inside a phase via Claude's own subagents); dual intake (founder files first; ledger import later, behind the ledger-hardening prerequisite of §2.3); the spec-PR gate with the founder's revised rules (§7, encoded exactly, with one refinement flagged in §7.3, and with the silence path **armed from day one** by founder ruling of 2026-08-21: no shadow period, no calibration-only posture); the depth dial, visible and overridable, with no gate skip at any depth; multi-task multi-project concurrency with leases; reeve merges on PASS with independent witnesses only, scoped to builder PRs and gated by the switches of §1.4; Rule 15; and, by founder ruling of 2026-08-21, **reeve is not cloud-hosted in the near future and must run on macOS, Windows, and Ubuntu**, macOS first and the other two as explicit later parity stages (the Platforms section, §14 S11 and S12).

**Standing invariants**: deterministic, durable, verifiable transitions; the model reasons only inside a phase; UNKNOWN never merges and absence is never success; escalation keys are identities, never reports; no optional safety parameter without same-commit call-site assertions (this design removes the parameter instead, §4.8); the actor is never the only witness; sandboxes restrict authority, network, and paths, never execution; nothing names reeve in a public or client repo; `claude` CLI on the founder's subscription, never the SDK; **no logical transaction ever spans two SQLite databases** (§1.3); **the server, not a local script, is the final merge enforcement point** (§9.1).

**Post-synthesis code facts reflected here (on main as of 2026-08-21)**: `lanes[].sensitiveOk` (tool-layer deny lift by verbatim territory claim plus per-file diff-gate exemption scoped to the declaring lane; quarantine and self-governing unreachable by any declaration); `flakeAssessment()` wired at FIX_CI dispatch (wholly-flaky escalates on an identity key with no attempt spent, mixed dispatches with the flaky job named as noise); `ESCALATIONS.PROTECTION_UNMET` for merges GitHub refuses beyond the clauses; profile `measured.review.*` rendering the 500-PR study into worker prompts with criticals-first findings ordering.

**Facts the lead verified live on 2026-08-21, which this revision is written against**:

- The live nextly sidecar profile already sets `authority.policy: propose_and_merge` and `merge.enforcement: enforced`. Repository authority is therefore not a dark switch and is not used as one anywhere in this document (§1.4, §9.1).
- The live `protect-main` ruleset requires a pull request, one approval, code-owner review, and an extra approval for unattributed changes; the only bypass actor is Organization Admin. Branch protection requires only `Decide what this commit can affect`; it does not require `ops/merge-policy` and does not bind that check to the merge-policy App (§9.1 makes both a go-live gate).
- No OS file-lock primitive is available to depend on: the audit found the usual one absent on this macOS host, and Node 24 exposes no binding for it (Appendix B). Every lock in this design is a lease row in hub.db or an atomic `wx` lock file, both of which are portable across the three target platforms (§1.2, §2.3, Platforms).
- `supervisor.mjs` spreads `...process.env` into workers (line 220) and swallows `onSpawn` failure (line 231); `daemon.mjs` swallows heartbeat failure (line 434). §4 reverses all three for both daemons.
- `backup.mjs` discovers only `~/.reeve/state/<owner>/*.db` and `restore` validates via an `event` table; a hub at `~/.reeve/state/hub.db` would have zero snapshots and no restore path (§11.4).
- Claude Code 2.1.237 exposes `--json-schema`, `--safe-mode`, `--strict-mcp-config`, `--bare`, `--effort`, `--max-budget-usd`, `--agents`, `--no-chrome`; `--print` silently ignores a settings file that fails validation; `--bare` disables OAuth/keychain authentication in this version (§4.4).

## 0. What this buys the founder

- File a task in one line (`reeve task file`). Ledger import arrives later, as its own separately enabled capability, once the ledger has a machine protocol (§2.3); until then every task is founder-filed.
- One thing to read per task: a plain-language spec PR in a **private** repo, with the sizing decision printed at the top and overridable by one comment. Every spec PR is reviewed by Codex until Codex finds nothing; then you get 15 minutes, measured from the moment reeve has demonstrably told you (§7.3), to approve, object, or say nothing. Silence after a delivered Codex-clean notice advances the task; silence without one never advances anything.
- Supervised autonomy during the pilot: implementation PRs still need your (or a code owner's) approval on GitHub, and reeve merges a builder PR only when its own witnesses, the guardian's verdict, and GitHub's server-side rules all agree (§9). Ordinary PRs are never auto-merged by this programme.
- One screen: `reeve dash` shows every task's state, the derived waiting reason (WAITING_FOR_CODEX, WAITING_FOR_NOTICE, WAITING_FOR_FOUNDER, WAITING_FOR_GUARDIAN, WAITING_FOR_QUOTA), and the single next action, from durable rows, never from a model's memory. UNKNOWN renders as UNKNOWN, never as quiet green.
- Notifications that name the one action needed, with the deadline in UTC and local time and the exact SHA prefix: "spec PR nextly-ops#12 clean by Codex at 14:02Z (19:02 PKT); reeve proceeds at 14:17Z unless you approve or comment; head a1b2c3d4e5."
- Full audit: `reeve task why bt:x` renders the evidence lineage (task generation, approved spec SHA, Codex source, founder or notice source, implementation SHA chain, guardian verdict, live server gate, merge receipt) from the rows the hub wrote at each step (§9.4, §11.6).
- Five independent capability switches (observe, draft-spec, implement-local, publish-pr, merge-builder-pr), each default off, so the programme widens one proof at a time (§1.4, §14).

## 1. Topology: a second process, one hub store, one writer per fact

### 1.1 Two processes

The guardian's dispatch loop is serial and awaits workers inline; a 20-minute worker already freezes verdict publishing for every other PR (daemon.mjs:359-365 and 445-458, `ctx.running` never maintained). A one-hour IMPLEMENTING phase inside that loop would blind the guardian for an hour. So the builder is **its own service-manager job** (launchd on macOS, a systemd user unit on Ubuntu, Task Scheduler on Windows; see Platforms), on macOS `com.revnix.reeve.builder` running `bin/reeve build run` with node pinned to the v24 binary (`~/.nvm/versions/node/v24.17.0/bin/node` on the founder's host; PATH node is v22). Guardian daemons (one per watched repo, per-repo DBs) are untouched except for the shared hardening §13 lists in full, none of which grants authority; the pieces that matter for the topology are the worker contract (§4), the provider scheduler claim before model dispatch (§10.4), the immutable receipt table in their own DB (§8.5), and one additive clause in their verdict that reads the hub's `pr_hold` table for builder PRs (§9.6). **The guardian's hub surface is exactly two touches**: it writes the provider scheduler (`provider_lease`, with its `provider_state` companion row, §10.4) and it reads `pr_hold` (read-only, §9.6). The guardian gains no merge executor in this programme, and it remains the **sole publisher** of the `ops/merge-policy` check; the builder never publishes a check run (§9, §13).

### 1.2 Single instance, enforced by a lease row

`reeve build run` claims a **singleton lease row** in hub.db at startup: `singleton_lease(name='builder', pid, lstart, command, acquired_at, expires_at)` written under `BEGIN IMMEDIATE`. The claim succeeds when no row exists, when the row's `expires_at` has passed and the recorded pid+lstart is provably dead, or when the row is owned by this same pid+lstart. The lease is heartbeated at lease/4 (LEASE_SECONDS=120, the proven ops.mjs contract); a heartbeat write that fails stops the builder loop (no new dispatch, no new effect) and terminates its live workers (§4.5). A second invocation prints the holder's pid, lstart, command, lease age, and expiry, plus the one recovery command (`reeve build run --takeover` after confirming the holder is dead; takeover re-runs the liveness check and refuses while the pid+lstart is alive). The service manager's instance and a founder-run terminal instance can never tick hub.db simultaneously, on any platform, because the lease lives in the database and not in an OS lock.

### 1.3 Stores and the single-writer rule

- **(a) Per-repo guardian DBs**: owned and written by the guardian alone. They gain one additive append-only table, `guardian_event` (§8.5, §11.3), which the guardian writes in its own transactions. The builder reads guardian DBs read-only over same-host WAL for exactly three purposes: verdict evidence at a head (§9.3 U1), receipt import (§8.5), and guardian liveness (§8.6). The builder never writes them.
- **(b) Hub DB** `~/.reeve/state/hub.db`: tasks, generations, phase events, phase runs with contract snapshots, approvals and gate rows, notice receipts, attested pushes, imported guardian receipts, the hub inbox and outbox, merge decisions, PR holds, harness acceptances, project authority rows, per-repo gate state, directory/territory/singleton leases, the provider scheduler, the append-only hub event table, and schema version. The builder is the hub's writer, with exactly one exception: both daemons write the provider scheduler tables (§10.4). The guardian's only other contact with hub.db is a read-only query of `pr_hold` from its verdict (§9.6); it touches nothing else.
- **(c) The nextly-ops ledger** (JSONL), written only through its own CLI, only after the hardening of §2.3, only from a dedicated builder-owned clone.
- **Transfers between stores are at-least-once and idempotent, never atomic across files.** SQLite cannot commit two database files atomically under WAL (a crash mid-commit can leave one committed and the other not), so no transition in this design writes two databases. Every fact that crosses a store boundary is an immutable event in its owner's store, imported by the consumer under a unique source key (§8.5 for guardian receipts; §2.4 for ledger events). A missing import makes the dependent clause UNKNOWN; it never makes the event illegitimate.

### 1.4 Capability switches

Authority is never inferred from repository profile fields (`authority.policy` is already `propose_and_merge` on the live nextly profile and is not a switch for anything in this programme). The builder exposes five independent switches, every one default false, all under `builder.capabilities.*` in the profile FIELDS validator, reported separately by `reeve builder doctor` and `reeve dash`:

| Switch | Profile key | What it enables |
|---|---|---|
| observe | `builder.capabilities.observe` | `reeve task file`, SIZING/RESEARCH/DESIGN workers, artifacts, dash, why. No external effect. |
| draft-spec | `builder.capabilities.draftSpec` | Spec worktree writes, spec-repo push, PR create, comments, review requests, the gate (§7). Private spec repo only. |
| implement-local | `builder.capabilities.implementLocal` | IMPLEMENT worktrees, controller acceptance and controller commit (§8.3, §8.4). No push. |
| publish-pr | `builder.capabilities.publishPr` | Implementation branch push and PR create on the project repo (§8.5). |
| merge-builder-pr | `builder.capabilities.mergeBuilderPr` | The hub merge coordinator may actuate (§9). Merge actuation requires **both** this switch and the process flag `reeve build run --actuate-merges` (the same two-key pattern as the guardian's `--execute`/`--enforce`); without both, the coordinator evaluates and records decisions but never enqueues a merge. There is no other merge key anywhere in the profile. |

**A switch is consulted before the transition that would need it, not after.** The loop never moves a task into a state whose first effect or dispatch is gated by an off switch: with `publishPr` off, an IMPLEMENTING slice completes acceptance and the controller commit and then **rests in IMPLEMENTING** (its run succeeded, the commit is recorded) with the derived substate `WAITING_FOR_CAPABILITY(publishPr)` shown in dash and `show`; with `implementLocal` off an approved task rests in APPROVED the same way. No escalation fires, because a switch is configuration the founder set, not a fault; doctor and dash name the switch. When the switch turns on, the loop takes the transition on its next tick. As defence in depth, the outbox executor and the dispatch seam also check the switch: an effect that reaches them while its switch is off settles with the hub-only status `refused` and a `capability.refused` event, is never retried by the executor, and is re-enqueued by the loop under its idempotency key once the switch is on. Compensations and annotations on a PR (`gh.pr.close`, hold and resume comments, body updates) are gated by the switch that created that PR: `draftSpec` for spec-repo PRs, `publishPr` for project-repo PRs; there is no builder `gh.check.publish` outbox kind at all (§9.6); the canary probe check of §9.1 is published by doctor directly, on the canary repository only, and is not an outbox effect. A switch may be turned on only at the rollout stage that proves it (§14). `mergeBuilderPr` has one further precondition it cannot satisfy on its own: the server must already require the App-bound `ops/merge-policy` check on the target repository. Making that check required on nextly's `protect-main` is the **guardian programme's capability-4 flip**, a founder decision taken after the verdict shadow week and documented in TRACKER Programme 1; the builder never flips it (§9.1, §14 S8). Until the builder's per-repo `repo_gate_state` row (§11.2, refreshed by the builder loop every tick, §9.1) shows the requirement in force, the switch is inert (clause U4 of §9.3 yields UNKNOWN) and `reeve builder doctor` reports "unsafe authority". The live negative merge probe (§9.1) is not a switch: it runs only from `reeve builder doctor --probe-live` against the profile-allowlisted canary repository `builder.canaryRepo`, and the switches above govern production PRs only. Ordinary PRs (anything without a bound `impl_pr` row) never reach the merge coordinator at all; their auto-merge is a separate future authorization, not a switch here (§9.2, §16).

### 1.5 Project registry and the registry snapshot

`~/.reeve/projects.json`: `{name: {repoPath, nwo, profilePath, worktreeRoot, specRepo?, ledger?}}`. Required because repo is NOT a ledger field; the ledger name is the project, and profiles are per-repo. The registry is mutable, so it cannot identify the configuration that admitted a task. At admission (§2.2) the builder resolves and stores on the task a **registry snapshot**: repository numeric id and nwo snapshot, repo path, profile path and profile hash, default branch, visibility, spec repository numeric id, gate-definition hash (§8.3), and registry version. Every later phase reads its configuration from the snapshot, not from the live registry; drift between the snapshot and the live registry is recorded and reported, and only the founder's `reeve task regenerate` adopts it (§4.7). Every new profile key (all `builder.*` knobs) is added to the profile `FIELDS` validator **first**, or every daemon start dies at profile load; profile documentation and examples are generated from the validator so they cannot drift (§11.6).

### 1.6 Determinism as code layout

`src/build/phases.mjs` exports `nextPhase(state, evidence)` returning a transition or a refusal, pure and total, unit-tested over the full transition matrix, held-state exits and CANCELLING included (§3.4, §3.5). Illegal transitions are refused and logged (`transition.refused` events; absence is never success). The model reasons only inside a phase worker.

### 1.7 Rule 15 at the moment of effect, with no cache

The boot-time check remains as the fast path: at builder startup, query the spec repo's visibility via the GitHub API by numeric id; anything other than exactly `private` refuses to run, and UNKNOWN visibility is not private. The check that actually protects Rule 15 lives in the **hub outbox executor**: every effect targeting the spec repo (push, pr-create, comment, review-request, body update, notice) **re-queries visibility with no TTL cache**, records the repository numeric id and the result on the outbox row, and refuses anything but exactly `private`: the task moves to BLOCKED and `bt:<id>:spec:visibility` escalates. Spec effects are low-volume; cache freshness is not worth weakening check-at-effect-time.

**Rule-15 lint on every public-bound effect.** For every outbox effect whose target repo is not verified private in this same execution, the lint runs over the **complete outgoing surface**: title, body, branch name, commit message, every changed path, generated metadata (labels, check summaries, comment markers), and case-folded token variants (`reeve`, `REEVE`, `Reeve`, `r-e-e-v-e` separated forms). A hit refuses the effect. Branch and actor naming are neutral by construction (§8.5): impl branches use the `mp/` prefix (after the App's own neutral slug `merge-policy`), and the App author line reads `merge-policy[bot]`. A private-repo URL in a public PR body can still leak private repository and task naming even when it contains no prohibited token; so public PR bodies carry the approval evidence (bound SHA, approval path) and no spec-repo URL at all (§8.5). `reeve builder doctor` asserts the App slug, branch templates, commit-message template, and check names contain no reeve token.

### 1.8 App credential handling

The merge-policy App (installation 155196718; Actions read, Administration read, Checks write, Contents write, Issues write, Metadata read, Pull requests write, Statuses write; Administration write refused in code) is the only publishing identity the builder has.

- Installation tokens are cached **in memory only**, refreshed shortly before expiry, never written to disk, never logged; a redaction assertion test greps every log sink for token shapes.
- There is **no founder-token fallback** anywhere: a missing App installation escalates (`builder:app-install:<repo>`) and the effect waits.
- The App token reaches git transport only in the **controller subprocess environment of a dedicated automation clone** (per project and per spec repo, under `~/.reeve/clones/<project>/`), never in a worker environment (§4.3) and never in the founder's live workspace.
- `reeve builder doctor` diffs the live installation permissions against the expected set, checks repository selection covers every registry project and spec repo, and reports drift as a configuration error (§11.6).
- Private-key rotation: generate the new key in the App settings, install it under the configured path, restart both daemons (doctor confirms a token mint), then revoke the old key; revocation of a compromised key is the same procedure with the revoke step first and every daemon halted until a new key mints.

## Platforms

**Founder ruling, 2026-08-21**: reeve is **not cloud-hosted** in the near future. It runs on the founder's own machines and must run on **macOS, Windows, and Ubuntu**. macOS is the first platform and every piece of evidence in this document was measured there; Ubuntu and Windows are explicit later rollout stages (§14 S11 and S12), each gated by the same canaries and the full suite run on that OS, and reeve's own CI runs the suite on all three operating systems by S11.

The matrix below **fails closed**: where a platform's mechanism is unmeasured, the capability that depends on it is refused on that platform rather than approximated.

| Concern | macOS (first) | Ubuntu | Windows | If the mechanism is unavailable |
|---|---|---|---|---|
| Native OS sandbox for workers (§4.2) | Seatbelt, measured | bubblewrap | unmeasured | **Write-capable workers (IMPLEMENT, SPEC) are refused on any host where the sandbox canary of §4.4 does not pass.** Read-only phases still require the canary; nothing falls back to an unsandboxed launch. |
| Service manager for the daemons (§1.1) | launchd | systemd user unit | Windows Task Scheduler | The daemons run only from a service-manager definition reeve generates; a founder terminal instance is a second instance and the singleton lease (§1.2) refuses it. |
| Process identity and group kill (§3.3, §4.5) | `ps` lstart plus `kill(-pid)` | same POSIX mechanism | needs a job object or `taskkill /T`, unmeasured | Without a proven group kill, adopt-or-kill cannot guarantee a dead worker before a worktree is touched, so dispatch is refused on that host until the mechanism is measured. |
| Notice delivery (§7.3) | ntfy (message id) plus `osascript` (exit status) | ntfy plus `notify-send` | ntfy plus Windows toast | Every configured channel must succeed (the existing `notify.mjs` rule); ntfy's message id and the desktop channel's successful exit are the references. A channel that yields neither fails the delivery, so no `notice_receipt` exists and the silence path never starts (§7.3 row 6). |
| Locks (§1.2, §2.3, §10.2) | lease rows in hub.db plus `wx` lock files | same | same | Already portable; no OS lock primitive is used anywhere. |
| Paths | `os.homedir()` for `~/.reeve`, `~/.claude` | same | same | No hard-coded `/Users` or `/home` path exists in reeve; doctor asserts it. |
| Off-device backup destination (§11.4) | a local machine, NAS, or disk | same | same | **Never a cloud service.** Same-disk snapshots run regardless; doctor reports the off-device copy as missing until a local destination is configured. |

`reeve builder doctor` reports the platform, which row of this matrix each mechanism resolved to, and the canary result, and classifies an unmeasured row as **unsafe authority** for the capabilities that depend on it.

## 2. Task intake

### 2.1 Identity and dedup

- Task id `bt:<ulid>` minted by the hub. Provenance is a durable fact: founder-filed `{source:"founder", filed_via:"cli", text_hash, idempotency_key}` or ledger import `{source:"ledger", ledger:"nextly", node_id:"task:x", claim_event_id, claim_operation_id, projection_generation}` (ledger provenance is by stable event and operation id, never by byte offset).
- `UNIQUE(source_kind, source_key)`: ledger node id for imports (collision is a hard refusal; the node is already owned), normalized-title sha256 for founder filings (collision is a warning plus `--anyway`; humans legitimately re-file near-twins). `--anyway` coexists with the constraint by salting: the re-filed task's `source_key` becomes `<title-hash>:<its own ulid>`, so the UNIQUE holds, the near-twin admits, and the provenance records that the collision was seen and accepted.
- `--idempotency-key <k>`: a second filing with the same key returns the existing task id and performs nothing, so a retried shell script cannot file twice.

### 2.2 `reeve task file`

```
reeve task file --project nextly --title "..." \
  --territory packages/x --territory packages/y/index.ts \
  [--body-file f.md | --body-file -] [--depth trivial|standard|deep] [--priority p1|p2] \
  [--idempotency-key k] [--pin-territory 48h] [--dry-run] [--json]
```

**Network first, transaction second.** The command resolves the registry snapshot (§1.5) over the network before it opens any transaction: repository numeric id, visibility, spec repository numeric id, default branch, and the profile hash are read and held as plain values. Only then does it open one `BEGIN IMMEDIATE` tx, which **receives those values and performs no I/O of its own**: task row with the snapshot and generation 1, `task.filed` event, territory child rows (§10.1), **and the territory lease grant with the full intersection check** (§10.2): **a filing whose territory conflicts with an active lease is refused in that tx**, naming the blocking task; nothing is inserted, no lease is granted, and the founder re-files later or narrows the territory (founder filings are never queued behind a lease; queueing and `lease:starved` apply to ledger candidates, §10.2). An admitted filing lands in FILED and takes the FILED → SIZING edge on the loop's next tick with no further condition. The hub write lock is therefore never held across a GitHub call. `--project` must resolve in the registry. `--dry-run` prints the resolved project, profile hash, normalized territory, conflicts it would hit, the depth floors that would fire, and the capability switches that are currently on, and writes nothing. `--json` returns the standard mutating-command shape of §11.6, `{task, prev, next, evidence_id, next_action}`, with `prev` null for a filing.

**Territory is REQUIRED at filing**, repeatable, and restricted to the canonical grammar of §10.1. A filing without `--territory` is refused with a message showing the flag and an example of the accepted grammar. An empty or unparseable claim, wherever one slips in, is treated as the repository root prefix (it conflicts with every lease in the project), never as no-claim: the absence of a territory claim must never read as the absence of conflict. Admission tests: a territory-less insert is refused; a root-prefix task blocks all concurrent grants in its project.

There is **no `--fast` flag and no gate skip of any kind** (§15.4): every task, however small, gets a spec PR; a trivial task just gets a short one. Pre-authorization at filing time binds to no head SHA, which is exactly the binding the gate exists to provide.

`--pin-territory <duration>` is the one way a task keeps its territory while held (§3.4, §10.2): filing prints a warning naming the expiry, dash shows the expiry beside the task, and the pin lapses at expiry without founder action.

### 2.3 Ledger intake is deferred behind a ledger-hardening prerequisite

The ledger today is a human CLI: `claim` is read/check/append with no operation id; projection applies the last claim unconditionally; `release` clears the current owner unconditionally; there is no JSON result contract; byte offsets are the only event identity and they move on rebase; `ledger sync` stages all of `ledgers/` and `decisions/` from whatever clone it runs in and can commit a human's unrelated work. Wrapping that in timing assumptions is not a protocol. So:

**Until the ledger ships the hardening below, intake is founder-filed only.** `reeve task import` exists as a command that refuses with the reason, and the `builder.capabilities.*` switches contain nothing that enables import; import is enabled at S5 (§14), separately from every other switch, behind `builder.intake.ledger.enabled` (default false).

**The prerequisite** (work in the nextly-ops repo, its own PRs, verified by `reeve builder doctor` before `builder.intake.ledger.enabled` may be set):

1. Every event carries an immutable `event_id`; every mutating request carries an `operation_id` (idempotency key) that a replay returns instead of re-appending.
2. `--json` output on `claim`, `release`, `note`, `add`, `link`, `fact`, `status`, and `sync`, returning the event id, the resulting owner, and the projection generation (a hash of the projected state after the append).
3. Conditional semantics: `claim <node> --if-owner null --operation-id <op>`; `release <node> --if-owner reeve:bt:<ulid>`. A failed condition appends nothing and exits non-zero with the current owner in the JSON.
4. Append with fsync; return the stable event id plus the projection generation in the same result.
5. **Narrow sync**: `ledger sync --paths <exact changed files>` stages only those paths, refuses to run in a clone that is dirty outside them, and returns the pushed commit.
6. A **dedicated builder-owned clean clone** of nextly-ops under `~/.reeve/clones/nextly-ops-ledger/`, never the founder's live workspace at `~/Work/Products/nextly-workspace/nextly-ops` (which was dirty at audit time and is a human's working tree). The nextly-integrations clone is dead and never touched.
7. A **portable lock**: clone-local serialization by an atomic `open(lockfile, 'wx')` under `OPS/ledgers/.nextly.lock` carrying pid+lstart, recovered by liveness check; the builder's own singleton lease (§1.2) serializes reeve against itself; remote optimistic verification (§2.4 step 5) settles the distributed race that no local lock can.
8. Hub provenance stores `event_id`, `operation_id`, and `projection_generation`, never a byte offset.

Two usages the earlier draft had wrong are corrected here and in §2.6: the note command is `ledger note "<text>" --node <id>`, and the write-back is `ledger add pr:N --kind pr --title "<title>"`.

### 2.4 The claim protocol once hardening ships (hub row first, claim as an outbox effect)

`reeve task import [--ledger nextly] [--limit N] [--pick <node-id>]` and the builder loop's auto-pick share one function:

1. **Candidate selection.** `ledger sync` in the dedicated clone. Candidates are unblocked plus unclaimed tasks, P1 bucket first, then `task:scout-*` (natural small work).
2. **Territory pre-check**: intersection (§10.1) of the candidate's territory against every active hub lease and every currently claimed ledger task's territory. Overlap: skip, and record a durable `candidate.skipped(territory, blocking_task)` row in `intake_event` (§11.2; a skipped candidate was never admitted, so it has no task id for `phase_event` to hold) so starvation is visible in dash, never silent. Enforcement is reeve-side because ledger territory is advisory only; `claim` never checks it.
3. **Hub tx FIRST** (the registry snapshot resolved over the network before the tx opens, exactly as in §2.2): insert the task row in phase **CLAIMING** with its registry snapshot, provenance, resolved copies of `{territory, body, research and decision refs}` from `DEPENDS_ON`/`DECIDED_BY` edges into `OPS/research/` and `OPS/decisions/` files (live files only; the archive folder is hook-blocked and never read), the territory lease grant, and an outbox row `ledger.claim` carrying a minted `operation_id`. The durable intent now exists before any external write.
4. **The outbox executor performs the ledger protocol** in the dedicated clone under the `wx` lock: `ledger note "reeve intends to build this" --node <id>`, then `ledger claim <id> --by reeve --lane reeve:bt:<ulid> --if-owner null --operation-id <op> --json`, then `ledger sync --paths OPS/ledgers/nextly.jsonl`. The JSON result's event id and projection generation are written to the outbox settle.
5. **Verify-after-push CAS**: re-pull, re-project. If the projected owner is not `reeve` (a human claim landed between the conditional append and the push, or a rebase re-ordered lines), reeve **lost**.
6. **On a lost race, reeve appends NOTHING to the ledger.** The human's later claim already supersedes reeve's line in projection; reeve's stale line is inert history. reeve marks the task **LOST** hub-side (quiet terminal state, no alarm) and releases the territory lease in the same tx. If the projection semantics ever require an explicit retraction, it is `release <id> --if-owner reeve:bt:<ulid>`, which by construction appends nothing when the human owns. The S5 race tests include the human-wins-after-reeve case: the human must remain projected owner.
7. **Crash anywhere in 4-6**: the outbox reconciler replays by `operation_id` (the ledger returns the existing event instead of re-appending) and finishes the story from ledger truth: reeve owns, complete and settle; a later owner exists, LOST; claim absent, retry or release the hub row. A startup sweep in `reeve build run` and a probe in `reeve builder doctor` cross-check the other direction: any ledger claim owned by reeve with no matching hub task escalates `bt:unknown:intake:orphan-claim`.
8. **The research gate, resolved empirically** (§15.1): the ledger's `claim` refuses any kind=task lacking a `DEPENDS_ON research:*` edge, and 0 of the 38 importable tasks have one. Two candidate protocols exist: (a) append `research:reeve-<task>` (status open) plus link, then claim without `--force` (conforms to the ledger's own discipline but may self-block the task, because `blockers()` blocks any task whose DEPENDS_ON target is not done or decided); (b) claim `--force true` with `force_reason:"research gate satisfied by builder RESEARCH phase"` recorded in the hub. **The S5 intake PR ships with a measurement** against a copy of the live ledger. If (a) does not self-block, it is the protocol; if it does, (b) is, with the reason durably recorded and the RESEARCH phase back-filling the real `research:` node, link, and `OPS/research/` file either way.
9. On claim success: CLAIMING transitions to SIZING; the claim event id and projection generation are stored so `reeve task why` points at the exact ledger event.

### 2.5 Ownership re-verification, every transition (ledger-sourced tasks)

Humans can `release` anyone's claim at any later moment. So: **before every phase transition** of a ledger-sourced task, reeve re-projects the dedicated clone's ledger file (cheap, in-memory). Before every transition that makes work visible outside this machine, it runs a full `ledger sync` first; that list is: **SPEC_PR_OPEN and every spec revision push, the start of each IMPLEMENTING slice, IMPL_PR_OPEN (the push and PR-create), every `reeve task resume` (§3.4), and the merge coordinator's pre-flight (§9.5)**. During VERDICT_WAIT the builder's poller repeats the full-sync re-verification each cycle and upserts the result as a durable `ownership_check` row (owner, sync timestamp); clause **B6** (§9.3) consumes it with a freshness bound and the pre-flight re-reads it live. If the projected owner is not reeve, the task goes to **BLOCKED** with escalation `bt:<id>:intake:ownership-lost`. reeve yields; it never fights a human for a claim. Test: remote re-claim mid-slice yields BLOCKED with no PR opened. Founder-filed tasks have no ledger owner; this section is out of scope for them by source kind, and every consumer records that explicitly.

### 2.6 Write-back on DONE

Exactly the lane grammar, through the typed CLI in the dedicated clone: `ledger fact <id> --evidence '<cmd> → <out>'`, `ledger status <id> done` (which releases), `ledger add pr:N --kind pr --title "<title>"` plus `ledger link pr:N --implements <id>`, `ledger sync --paths ...`. Corrections are new events (REFUTES/SUPERSEDES), never edits. Each step carries an `operation_id`, so a crash-rerun of FINALIZING replays rather than duplicates.

## 3. The task state machine

### 3.1 States

```
FILED → SIZING                          (founder-filed)
CLAIMING → SIZING | LOST                (ledger-sourced, after S5: inserted directly in CLAIMING, §2.4.3)
SIZING → RESEARCH → DESIGN → SPEC_DRAFT → SPEC_PR_OPEN → GATE
SIZING → DESIGN                         (trivial depth, §5: RESEARCH skipped by
                                         a recorded research.skipped event)
GATE → APPROVED | SPEC_DRAFT (REVISE: Codex findings or a founder
                                         changes-request, carried as the input) | DESIGN (depth override, §5)
SPEC_DRAFT → DESIGN                     (depth override, §5)
SPEC_PR_OPEN → DESIGN                   (depth override, §5)
APPROVED → IMPLEMENTING(slice k) → IMPL_PR_OPEN(k) → VERDICT_WAIT(k) → SLICE_MERGED(k)
SLICE_MERGED(k) → IMPLEMENTING(k+1) | FINALIZING → DONE
IMPLEMENTING(k) → BLOCKED              (over-budget slice or undeclared overrun, §8.2;
                                         held_from=IMPLEMENTING; NO edge back to SPEC_DRAFT)
any worker phase: attempt fails → same-phase retry (bounded, §4.6) | ESCALATED
                                        (PHASE_FAILED is a phase_run OUTCOME, never a state)
GATE → ESCALATED                        (revision cap reached, §7.3 row 1; the only
                                         ESCALATED entry that is not a worker phase's retries exhausted)
any non-terminal except CANCELLING → BLOCKED   (reason recorded with held_from; a HELD state)
BLOCKED → held_from phase | DESIGN      (founder: reeve task resume [--redesign], §3.4)
ESCALATED → held_from phase | DESIGN    (founder: reeve task resume [--redesign]; fresh
                                         budget as defined per phase in §3.4)
any non-terminal except CANCELLING → INFEASIBLE   (reason required; a success state)
any non-terminal except CANCELLING → CANCELLING → CANCELLED (founder cancel; CANCELLED only
                                         after every leased external effect reconciles, §3.5)
claim race lost → LOST                  (quiet terminal)
```

"any non-terminal" means exactly that: every state except DONE, CANCELLED, LOST, and INFEASIBLE. **CANCELLING is excluded as a source from every "any non-terminal" edge** (it exits only to CANCELLED), and both held states are included (a founder may cancel or mark INFEASIBLE a BLOCKED or ESCALATED task). ESCALATED has exactly two entry edges: a worker phase whose bounded retries are exhausted (§4.6), and `GATE → ESCALATED` at the revision cap; `phases.mjs` lists both explicitly and refuses every other source. There is **no IMPLEMENTING → SPEC_DRAFT edge**: a plan that turns out wrong during implementation is a founder decision (BLOCKED, then `resume` or `resume --redesign`), never an automatic spec revision (§5, §8.2). INFEASIBLE is a success state that is still never quiet: its entry tx raises `bt:<id>:infeasible` (identity; the reason rides in the body) so the founder reads why work stopped; it is the one builder escalation retired by the terminal state itself once the notification is delivered, because there is no founder action to wait for.

**The authoritative enumeration** (this list is the `task.phase CHECK` and the domain of `phases.mjs`; nothing else is a state): active: FILED, CLAIMING, SIZING, RESEARCH, DESIGN, SPEC_DRAFT, SPEC_PR_OPEN, GATE, APPROVED, IMPLEMENTING, IMPL_PR_OPEN, VERDICT_WAIT, SLICE_MERGED, FINALIZING; held: BLOCKED, ESCALATED; draining: CANCELLING; terminal: DONE, CANCELLED, LOST, INFEASIBLE. There is no REVISING state: a revision is the transition GATE → SPEC_DRAFT carrying the findings (or the founder's changes-request) as input, and **`BUILD_SPEC` runs in SPEC_DRAFT for the first draft and for every revision alike**; §3.2's idempotency keys and §4.1's action table use SPEC_DRAFT for that reason. PHASE_FAILED is a `phase_run` outcome, not a state. **A hold event on a task that is already held does not transition it**: `spec:reopened`, `ownership-lost`, or any other hold arriving while the task is BLOCKED or ESCALATED appends a `hold_reason(task, reason, at)` row (§11.2), keeps the original `held_from`, and updates the reason on the existing open `pr_hold` row instead of inserting a second one (the `one_open_hold` index stays satisfied); `reeve task resume` lists every stacked reason and clears them all in its tx.

**Terminal states**: DONE, CANCELLED, LOST, INFEASIBLE; no transition leaves them. **Held states**: BLOCKED and ESCALATED; each has exactly one founder exit verb (§3.4). **Draining state**: CANCELLING (§3.5), which exits only to CANCELLED. The machine is total: every state either advances by evidence, is terminal, is held with a specified exit, or is draining toward a terminal.

DESIGN must emit an ordered list of PR-sized slices (§8.2); the slice cursor is durable. This is how the 500-PR finding (crossing about 10 changed files roughly triples review rounds, 1.34 to 4.29) becomes structure rather than prompt hope, as a default reviewability budget, not a universal ceiling (§8.2).

### 3.2 Transition discipline: one shape, everywhere, generation-fenced

**Two counters, with different jobs.** Every task carries an integer `generation`, starting at 1: the **contract epoch**. It bumps **only on two founder commands**: `reeve task resume --redesign` (§3.4) and `reeve task regenerate` (§4.7, the deliberate adoption of a changed contract). A depth override never bumps by itself: before APPROVED nothing is bound yet and the phase simply re-dispatches as a new attempt; after APPROVED it holds the task (§5), and the founder's choice of a plain `resume` (generation unchanged, approval intact, the override recorded but inert) or `resume --redesign` (bump) decides. Everything that merely repeats work is counted by **`phase_run.attempt`**: retries after a failed attempt, adopt-or-kill replacements (§3.3), the single BAD_REPORT retry (§4.6), and a plain `reeve task resume` all start a new attempt and **never bump the generation**. Approvals bind to the pair (spec head SHA, generation) (§7.3), so a retry, a crash, or a plain resume cannot void an approval; only `--redesign` or `regenerate`, each of which changes what was approved, starts a new epoch that must be approved again. Every transition is exactly one `BEGIN IMMEDIATE` tx that:

1. **CAS-updates the projection**: `UPDATE task SET phase=:to, generation=:g_next, updated_at=:now WHERE id=:task AND phase=:expected AND generation=:g`, where `:g_next` equals `:g` for every transition except the two deliberate bumps above. Zero rows changed means a concurrent actor won: a no-op, never an error. A phase-only CAS would let a stale attempt from generation 3 act on a task that was redesigned into generation 4; the generation column in the predicate closes that.
2. Appends the `phase_event` row (new builder op names only; guardian event ops are never reused or renamed) and the `hub_event` row (§11.2) that backup replay reads.
3. Records the artifact sha256 that justified the transition.
4. Enqueues any side effect as a hub outbox row, never performing it inline. Every outbox row carries `task_id`, `task_generation`, a `fence` token (the phase_event seq that enqueued it), and `cancellable` (true for anything the §3.5 drain may void). The executor **revalidates the fence before actuation**: the task must still be at the recorded generation and the row must not be voided, re-read inside the lease tx; otherwise the row settles as `fenced` with no effect.
5. **For transitions into CANCELLING, BLOCKED, LOST, or INFEASIBLE**: voids the task's pending cancellable outbox rows in the same tx, records the set of **in-flight** rows that must reconcile before the state may settle (§3.5), enqueues the compensating effects (close an open PR with an explanatory comment for terminal paths; annotate-and-hold for BLOCKED), writes a **`pr_hold` row for every open builder PR** the path leaves behind (§9.6; the guardian's verdict reads it and renders BLOCK, so the server-required check fails), records `held_from` for BLOCKED, and releases the task's territory lease (§10.2). **For transitions into ESCALATED**: voids nothing (the phase merely stopped and its effects stand), writes `pr_hold` for any open builder PR, and releases the territory lease exactly like BLOCKED unless a live `--pin-territory` holds it (§3.4, §10.2).

**A transition commits only after its phase artifact is durable**: written tmp+rename+fsync to `~/.reeve/tasks/<bt>/artifacts/<phase>.{md,json}`, sha256 in the event, and (RESEARCH onward) committed to the spec branch.

**Side effects** run only through the hub outbox: the guardian's proven DDL and `enqueue/leaseOutbox/settleOutbox/recoverOutbox` shapes extended with the columns above and two hub-only statuses, `voided` and `fenced`; expired in-flight rows are not silently returned to pending, they are routed to their reconciler first (§3.3). Idempotency keys **carry the generation**: `bt:<id>:g<generation>:<phase>:<kind>:<n>` generally, `bt:<id>:g<generation>:<phase>:<kind>:<sha>` for push and merge kinds, and **`bt:<id>:g<generation>:r<resume_seq>:SPEC_DRAFT:push:<round>`** for spec pushes (round 0 is the first draft; `resume_seq` makes a round re-minted after a GATE resume, §3.4, a distinct key), keyed by the gate round being answered rather than by content: a crash-rerun of a SPEC_DRAFT revision re-derives different bytes and therefore a different commit SHA, so a content-keyed push would duplicate the revision; a round-keyed push maps the rerun to the same key and is inert. **The spec PR is reused across epochs**: the branch `reeve/spec/bt-<id>` and the PR are fixed for the task's life; a `--redesign` epoch pushes a new head to the same branch, and its `pr-create` row (a distinct key because the generation is in it) settles inert because the reconciler finds the existing PR by head branch. The gate keys everything by head SHA, so a reused PR is no ambiguity. **Key uniqueness is over live rows only** (`UNIQUE(idempotency_key) WHERE status IN ('pending','inflight')`, §11.2): a completed, voided, fenced, or failed row is history, so a re-enqueued key (a plain resume from BLOCKED, which voided rows, or from ESCALATED, which voided nothing and whose prior rows are `done`) is admitted as a new row beside it and settled by its reconciler against external truth, which is what makes re-delivery inert; without that rule the dedup would either swallow the re-enqueued effect or refuse it on a unique violation. **For round-keyed and sha-keyed kinds the enqueue additionally consults completed rows**: if a `done` row with the same key exists, the new row is settled `superseded` at enqueue with no effect performed, because for those kinds the key itself is the proof that the effect happened (a re-derived revision with different bytes must not become a second push for the same round); for every other kind the reconciler decides against external truth. The revision cap counts distinct findings-rounds (gate_request rows minted per round), never raw pushes. Test: kill between push settle and transition commit; exactly one revision exists for that round.

### 3.3 Resume after crash or restart

On builder start (service-manager relaunch), after the singleton lease is held (§1.2):

1. `recoverOutbox`: every leased-but-unsettled side effect is settled by its **reconciler against external truth** (push via ls-remote, pr-create via search by head branch, comment via list by marker, merge via `mergedAt`, notice via the channel's delivery receipt, ledger claim via `operation_id` replay per §2.4.7; `pr_hold` is a hub row, not an external effect, and needs no reconciler). Never from what the process remembered. A row whose fence no longer validates settles as `fenced`.
2. **Adopt-or-kill for surviving workers.** Workers spawn detached (process-group leaders), so a builder crash does not kill them. For each recorded live run, check pid+lstart. If the process is alive **and its run lease has not expired**, adopt it: re-take the lease under the recorded generation, poll its durable output file to completion, then parse and proceed. If the lease has expired, or adoption is not possible (session ambiguity, budget exceeded, contract snapshot missing), SIGTERM then SIGKILL the recorded process **group**, and only after confirmed death mark the run `attempt_failed(cause:crash)` and touch the worktree. **Never dispatch into a worktree whose recorded owner pid is alive.** This is consistent with §4.5: lease loss always ends in termination; adoption is the narrow case where the lease is still live because the restart happened inside one lease window.
3. **Durable worker output files** make adoption possible: every worker's stdout and stderr are streamed to bounded run-scoped files under `~/.reeve/tasks/<bt>/runs/g<generation>-<phase>-s<slice>-a<attempt>.{out,err}` (§4.5; `s0` for phases without a slice). Workers also carry parent-independent bounds: `--max-turns` and `--max-budget-usd` are enforced by the CLI itself, so an orphan cannot burn the subscription indefinitely even with no parent watching.
4. Each non-terminal task resumes **at its current phase from its durable artifacts** under its **contract snapshot** (§4.7): fresh worker session, artifacts as input, never a resumed conversation. **Exactly two exceptions** may `--resume <sessionId>` instead of starting fresh: an attempt interrupted by a rate limit or a timeout, and the single BAD_REPORT retry of §4.6. Both go through the same dispatch seam as a fresh launch (§4.8), with the full argv rebuilt and the contract snapshot reused verbatim; both are new `phase_run.attempt` rows and neither bumps the generation (§3.2). §4.6 states the same two exceptions in the same words.
5. A crash mid-phase re-runs the whole phase. Safe because phases are idempotent-on-rerun: report phases overwrite their artifact; code phases re-derive the diff in a fresh worktree, with one exception: a slice resumed with `--accept-harness` does not re-derive, it re-applies the preserved, hash-verified patch (§8.3); side effects are outbox-deduped, with the round-keyed exception of §3.2.

Tests: kill -9 mid-RESEARCH and mid-`gh.pr.create` (exactly one PR, phase completes); kill -9 mid-IMPLEMENT with the worker surviving inside its lease window (restart adopts, report parsed from file); kill -9 with the lease expired (group killed, worktree touched only after death).

### 3.4 Held states: BLOCKED, ESCALATED, and `reeve task resume`

BLOCKED and ESCALATED are **held**, not terminal, and each has a specified exit, so `phases.mjs` stays pure and total.

- **BLOCKED entry** records `blocked_reason` and `held_from` in the entry tx, with the §3.2.5 compensations: pending outbox rows voided, annotate-and-hold effects enqueued, territory lease released.
- **ESCALATED entry** (from a worker phase whose bounded retries are exhausted, or directly from GATE at the revision cap, §3.1, §7.3 row 1) keeps the escalation standing until the founder acts. It does **not** void outbox rows (the phase merely stopped), but it **releases its territory lease exactly like BLOCKED**: a provider failure that waits for a founder must not starve every overlapping task for as long as the founder is away. The one exception is an explicit `--pin-territory` (§2.2) whose expiry has not passed; dash shows the pin and its expiry, and `bt:<id>:lease:starved` still fires on the holding task when the pin produces skips past `builder.lease.starvedHours`.
- **`reeve task resume <id> [--redesign] [--accept-harness <hash-prefix>] [--pin-territory d]`** (founder-only; the exit verb for both held states) runs one `BEGIN IMMEDIATE` tx that re-establishes the admission preconditions before any CAS:
  1. **Territory lease re-grant** through the identical §10.2 intersection check. If the territory now conflicts, resume refuses and names the blocking task; nothing transitions and no lease is granted.
  2. For ledger-sourced tasks, **ownership re-verification with a full `ledger sync` first** (§2.5): if the projected owner is not reeve, resume refuses.
  3. CAS transition `BLOCKED → held_from` or `ESCALATED → held_from` with the **generation unchanged** (a plain resume repeats work under the approved plan, so the approval survives, §3.2), or `BLOCKED → DESIGN` and `ESCALATED → DESIGN` with `--redesign` (valid from either held state; used after `spec:reopened`, post-approval depth overrides, an over-budget slice, or a revision loop the founder would rather restart from the design, §5, §7.5, §8.2), which **bumps the generation**: a new contract epoch whose spec goes through the full gate again as a new head. `--redesign` converts the hold annotations into terminal-style compensations in the same tx: any open slice PR is closed with an explanatory comment. Every resume clears the task's `pr_hold` rows (`cleared_at`) in the same tx, so a re-entered slice PR is no longer held (§9.6).
  4. A `task.resumed` event, plus a compensating "resumed" annotation enqueued for any hold comment the entry left.
- **Fresh budget, defined once here.** Re-entering `held_from` gives the phase a fresh budget, and what "fresh" means depends on the phase: for worker phases (SIZING, RESEARCH, DESIGN, SPEC_DRAFT, IMPLEMENTING) the **attempt budget resets**: the bounded retries of §4.6 are counted from the `task.resumed` event (each run row records the `resume_seq` it ran under, §11.2), while attempt numbers themselves stay monotonic per (task, generation, phase, slice) and are never reused, so a resumed run can never collide with an earlier run row; for GATE the **revision-round counter resets**, so the ten-round cap of §7.3 starts again from the current head (the held task re-enters GATE and the next Codex findings open round 1); for VERDICT_WAIT the staleness clock of §8.6 restarts. The generation is unchanged in every case.
- **`--accept-harness <hash-prefix>`** is the **only writer** of `harness_acceptance` rows (§8.3, clause B7 of §9.3). It is valid only when the hold is `impl:harness-touched`: the command re-computes the hash of the **preserved held patch** (written durably at hold time, §8.3) against the approved base, refuses if the supplied prefix does not match it (printing the held hash so the founder can compare), and otherwise records `harness_acceptance(task, generation, slice, diff_hash, actor_id, accepted_at)` in the same tx as the transition. The resumed IMPLEMENTING slice then **re-applies that exact patch** instead of dispatching a worker (§8.3), so the hash the founder accepted is the hash of the diff the PR carries. No other command, event, or comment can write that row, so a harness change is accepted only by a founder who named the exact diff.
- **Voided rows stay voided.** The re-entered phase re-derives and re-enqueues its own effects under the standard idempotency keys, which carry the generation (§3.2): a plain resume re-enqueues at the **same** generation, and because key uniqueness is over live rows only, the new row is admitted beside the voided (or already-done) one; after `--redesign` the new generation makes every key distinct by construction. Where an effect already happened externally before the hold, the reconcilers settle the re-enqueued row as inert against external truth, never as a duplicate.

Tests: resume re-grants the lease and is refused when the territory now conflicts, naming the blocker; resume of an ownership-lost task refuses while a human is still projected owner and succeeds after the founder re-establishes reeve's claim; resume with `--redesign` closes the open slice PR, lands the task in DESIGN, and bumps the generation; a plain resume leaves the generation and the approval row valid; `--accept-harness` with a wrong prefix refuses and writes nothing; a GATE task resumed from the revision cap gets ten fresh rounds; an ESCALATED task's territory is claimable by a concurrent filing; the S2 transition-matrix test covers every held-state exit.

### 3.5 CANCELLING: a cancel is final only when the world agrees

`reeve task cancel <id>` moves the task to **CANCELLING** in one tx (§3.2.5): pending cancellable rows are voided, the ids of every **in-flight** leased row (a push mid-transport, a PR create mid-request, a merge whose pre-flight has started) are recorded as `drain_set`, a `pr_hold` row is written for each open builder PR in the same tx (§9.6; the guardian's verdict reads it and renders BLOCK, so the server-required `ops/merge-policy` check fails at the next guardian tick), compensations are enqueued (close the spec PR and any open slice PR with a comment), the territory lease is released, and the live worker, if any, is terminated through §4.5. The task becomes **CANCELLED** only when every row in `drain_set` has settled through its reconciler (done, fenced, or failed, each against external truth) and every compensation has settled. A task is never CANCELLED merely because pending rows were marked void. Dash renders CANCELLING with the count of rows still draining; `bt:<id>:cancel:draining` escalates if the drain exceeds `builder.cancel.drainMinutes` (default 30). **CANCELLING has exactly one founder exit**: `reeve task cancel <id> --force`, valid only after `drainMinutes` has passed, records every unreconciled `drain_set` row as `forced` (with what is known about it from its last reconciler attempt), moves the task to CANCELLED, and leaves the `cancel:draining` escalation standing until the founder retires it with `reeve task resolve <id>` (the verb for acknowledging a standing escalation on a terminal task; `ack` is the gate notice acknowledgment and refuses outside GATE, §7.3), because a forced cancel is the one terminal transition whose external truth was not confirmed. `reeve task why` renders the forced rows. The merge coordinator treats CANCELLING exactly like CANCELLED (clause B3, §9.3).

**Cancel during CLAIMING** (ledger-sourced tasks, S5 onward): if the `ledger.claim` effect already landed, the hub row is not the only record of the claim, so the cancel tx enqueues one more compensation, the outbox effect `ledger.release` running `release <id> --if-owner reeve:bt:<ulid>` through the typed CLI in the dedicated clone; it appends nothing when a human already owns the node, and the orphan sweep of §2.4.7 therefore never finds a reeve-owned claim for a CANCELLED task. Until S5 this path cannot occur, because intake is founder-filed only and CLAIMING is unreachable.

Test: merge row leased, cancel committed, API call attempted: the pre-flight re-read refuses, the row settles `fenced`, the hold row exists and the guardian's next verdict at H renders BLOCK, the PR closes, and only then does the task read CANCELLED.

## 4. The worker contract (guardian-shared)

This section is the first thing built (§14, S1). It applies to every `claude` worker either daemon launches: builder phases and guardian FIX_CI and review-thread workers alike. It grants no authority; it removes ambient authority the workers have today.

### 4.1 Phases

All workers dispatch through the existing supervisor (`workerArgs`/`runWorker`: repo-agnostic cwd, detached group, SIGTERM-then-SIGKILL budget, halt-poll failing closed, retry bound), extended as below. Builder actions are new cases in `sandboxFor`'s per-action switch and new cases in `promptFor`, the intended extension seams.

| Phase | action | cwd | tools beyond profile base | network | budget | turns | model/effort | product |
|---|---|---|---|---|---|---|---|---|
| SIZING | `BUILD_SIZE` | read-only clone of project repo | Read/Grep/Glob only | none | 8 min | 15 | sonnet / low | `sizing.json` |
| RESEARCH | `BUILD_RESEARCH` | read-only clone plus `--add-dir` OPS research/decisions | read tools, `Agent(*)`, WebSearch, WebFetch | built-in web tools plus the profile's research domain allowlist, Bash network otherwise denied | 20-60 min by depth | 60 | fable / high | `research.md` |
| DESIGN | `BUILD_DESIGN` | same | read tools, `Agent(*)` | none | 20-60 min | 60 | fable / high | `design.md` with slice list |
| SPEC_DRAFT (first draft and every revision) | `BUILD_SPEC` | spec worktree (dedicated spec clone) | read plus Write/Edit scoped to `specs/bt-<id>/**` | none | 20 min | 30 | fable / high | spec files on disk |
| IMPLEMENTING | `BUILD_IMPL` | per-(task,slice) worktree | Write/Edit/Bash(test/build/lint pnpm scripts) | none | 60-90 min | 120 | fable / high | diff plus report |

- **Per-action knobs** in the profile: `builder.budgets.<action> = {budgetMinutes, maxTurns, model, effort, maxBudgetUsd, maxAttempts}` (`maxAttempts` default 3: the first attempt plus two retries, counting every failure cause alike: timeout, lease_lost, settings_invalid, crash, and the single BAD_REPORT resume; when it is exhausted the task goes to ESCALATED). Added to `FIELDS` first, same PR.
- **Every prompt states its own budget, turn cap, and reviewability budget in-text**: a budget the agent cannot see is a budget it cannot plan within. Prompts follow the proven prompts.mjs pattern (invariants-from-profile, honest current state with verification commands, full prior artifacts inlined, never summaries of summaries, and an output contract that matches the `--json-schema` of §4.6), and render `measured.review.*` where the profile carries it. Prompts also state: "BLOCKED or INFEASIBLE with a reason is a success outcome; salvage is not." **How a worker's report becomes a transition**: every phase schema (§4.6) carries `outcome` in `{ok, blocked, infeasible}` and a `reason`; reeve, not the worker, performs the transition after validating the report: `infeasible` moves the task to INFEASIBLE with `task.terminal_reason` set from the report and `bt:<id>:infeasible` raised; `blocked` moves it to BLOCKED with `held_from` the current phase, `blocked_reason` from the report, `pr_hold` reason `blocked_other`, and `bt:<id>:phase:blocked:<phase>` raised (§11.7), so a worker that stops for a reason always reaches the founder.
- Dependency installation is a **controller step before dispatch** (`pnpm install --frozen-lockfile` in the worktree, under the controller's own network), because the worker has no Bash network. A slice that needs a lockfile change reports it; the controller performs the install in its own step and re-runs the gates (§8.3).

### 4.2 OS-enforced sandbox

Workers run under Claude Code's native OS sandbox (Seatbelt on macOS, bubblewrap on Ubuntu; Windows is unmeasured and write-capable workers are refused there until the canary passes, see Platforms), enabled in the generated settings file with fail-if-unavailable and no unsandboxed fallback: `sandbox.enabled=true`, `sandbox.failIfUnavailable=true`, `sandbox.allowUnsandboxedCommands=false` (the exact key names are confirmed against the installed CLI's documentation in the implementation plan for S1; the three properties are the contract). Filesystem write scope is the worktree, the run's scratch dir, and the CLI's own state directory under `~/.claude` (the CLI needs it for subscription authentication and session files, §4.3), and nothing else; read scope adds the `--add-dir` paths the phase names. Network: denied for IMPLEMENT, SPEC, DESIGN, and SIZING; for RESEARCH the built-in web tools are explicit tools and Bash network is limited to `builder.network.research.allowedDomains` (default empty). Containment is by authority, not string patterns: the subcommand-prefix denies (`Bash(git push:*)`) remain as documentation of intent, and the design says plainly that they enforce nothing (`git -C . push <url>` slips every pattern while `Bash(git:*)` permits it). Publishing is impossible because no credential exists in the worker (§4.3), the sandbox denies network, each worktree carries a pre-push hook that refuses all pushes, and the bogus per-worktree `pushurl` stays as a further layer. The `NEVER` list still strips `gh` publishing surfaces for every action; workers that need GitHub effects don't get grants; reeve performs the effect through the hub outbox.

### 4.3 Environment allowlist

`runWorker` never spreads `process.env`. The worker environment is built from an explicit allowlist: `PATH` (pinned to the node v24 and pnpm bins plus system paths), `HOME` (the founder's real home, see below), `TMPDIR` (per-run), `LANG`, `TERM`, `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` (§6), the credential-less git variables below, and the per-phase variables the contract names. Stripped by construction, with a test that asserts their absence in a spawned worker's `env`: `GH_TOKEN`, `GITHUB_TOKEN`, `SSH_AUTH_SOCK`, every `AWS_*`, `GOOGLE_*`, `AZURE_*`, `*_PROXY`/`*_proxy`, `GIT_SSH_COMMAND`, `GIT_CONFIG_*` overrides other than the ones below, `GIT_ASKPASS`, and the reeve App key path.

**HOME is not isolated, on purpose.** The `claude` CLI reads `~/.claude` and `~/.claude.json` for the founder's subscription authentication and account state; a per-run home would leave every worker unauthenticated (the same reason `--bare` is deferred, §4.4). So workers see the real `HOME`, and isolation comes from everything else: `--safe-mode`, the explicit `--settings` file, `--strict-mcp-config`, `--no-chrome` (§4.4), this environment allowlist, a **credential-less git**, and the OS sandbox's network deny for every phase except RESEARCH (§4.2). Credential-less git is four settings: `GIT_CONFIG_NOSYSTEM=1` (the system config is never read), `GIT_CONFIG_GLOBAL=<a reeve-owned config file>` whose content sets `credential.helper=` (empty, which disables every helper) and carries no URL rewrites, `GIT_TERMINAL_PROMPT=0`, and no `SSH_AUTH_SOCK`; the founder's own `~/.gitconfig` and keychain helper are therefore unreachable even though `HOME` points at them. No API key variable is passed. **S1 measures that subscription authentication still works under exactly this allowlisted environment**: `reeve builder doctor` runs a one-turn authenticated probe worker with the production env and reports the result, and a failing probe refuses every dispatch.

### 4.4 Ambient-settings isolation

The founder's user settings carry broad Git/GitHub permissions, plugins, extra directories, and no sandbox block; a worker must not inherit them. Every dispatch passes `--safe-mode`, an explicit `--settings <generated file>`, `--strict-mcp-config` (with an empty MCP config unless the phase names servers), `--no-chrome`, explicit `--allowedTools`/`--disallowedTools`, and explicit `--agents` (§6). `--bare` is not used until subscription authentication under bare mode is proven on the installed CLI, because this version disables OAuth/keychain authentication in bare mode (§16, Appendix B N1). **A supplied settings path is not proof**: `--print` silently ignores a settings file that fails validation. So the supervisor validates the generated settings against the CLI's schema before spawn (a validation failure is a dispatch failure, `phase.attempt_failed(cause:settings_invalid)`, never a launch), and runs a **sandbox canary** once per contract hash per daemon start: a 30-second worker that attempts a write outside its scope and a network connect; both must fail, or every dispatch under that contract is refused and the raising daemon escalates in its own store (`builder:sandbox:canary-failed` from the builder, `guardian:sandbox:canary-failed` from a guardian daemon, §11.7). The canary is also the per-platform proof the Platforms matrix depends on: on a host where it does not pass, write-capable workers are refused outright.

### 4.5 Spawn binding, lease, and durable streams (fail closed, both daemons)

- **Every run has a row, in the daemon's own store.** The builder records a run in hub `phase_run` (§11.2); a guardian daemon records one in the additive per-repo table `worker_run` (§11.3), written at dispatch and keyed by the existing `run` row, which already carries the guardian's lease (`lease_expires_at`, `heartbeat_at`); `worker_run` holds the contract snapshot and the durable paths, never a second lease. The two tables share one column family (CLI version, resolved model, effort, argv hash, prompt hash, settings hash, tool contract, max turns, max budget, out and err paths, pid, lstart), so the contract snapshot of §4.7 and the bindings below have the same home in both daemons; no guardian evidence lives in the hub and no builder table lives in a guardian DB.
- **`onSpawn` persistence fails closed.** If the run row cannot commit pid+lstart (DB error, constraint, disk), the supervisor kills the process group immediately and reports no run. There is never a worker without a durable binding.
- **Heartbeat or lease loss revokes authority and terminates the worker.** The run lease is heartbeated at lease/4; a heartbeat write that fails, or a lease found expired (or, for builder runs only, recorded under a generation the task has since left), terminates the process group (SIGTERM, then SIGKILL after the budget) and records `attempt_failed(cause:lease_lost)`. The former posture ("a missed beat must not kill the worker") is reversed for both daemons: a worker that cannot prove it is still leased must not keep acting.
- **stdout and stderr stream to bounded durable files** (`~/.reeve/tasks/<bt>/runs/g<generation>-<phase>-s<slice>-a<attempt>.{out,err}` for the builder; the guardian's existing run dir for guardian workers), capped by the shared profile key `worker.maxOutputBytes` (default 64 MiB, read by both daemons, added to `FIELDS` in S1) with truncation recorded on the run row. Nothing accumulates unbounded in supervisor memory; `parseReport` reads the file.

### 4.6 Reports and acceptance

- **Phase reports use CLI-native structured output**: each action's dispatch passes `--json-schema <phase schema>`; the CLI's final structured result is read from the durable output, validated locally against the same schema, and stored by hash. Malformed or missing structured output is a failure (`BAD_REPORT`), never a transition; one retry `--resume`s the same session with the schema and parse error quoted, then the attempt budget is exhausted, the task goes to ESCALATED, and `bt:<id>:phase:failed:<phase>` escalates. That retry is one of **exactly two exceptions** to the fresh-session rule (the other is an attempt interrupted by a rate limit or a timeout, §3.3 step 4); both go through the same dispatch seam as a fresh launch (§4.8), with the full argv rebuilt and the contract snapshot reused verbatim; both are new `phase_run.attempt` rows and neither bumps the generation (§3.2).
- **Acceptance is machine-checked, never self-reported.** The report is trusted only for "why did you stop". Success means the artifact exists, parses, meets minima (research.md: at least one file:line citation per claim), and for IMPLEMENT, **the controller re-runs the gate commands itself** through the wrapper of §8.3 and records exit codes plus output hashes as evidence.
- **`reviewArtifact` is a sibling function, not a parameter**: report phases (SIZING/RESEARCH/DESIGN) are gated by `reviewArtifact({phase, dir, expect})`; diff phases (`BUILD_IMPL`, `BUILD_SPEC`) keep `reviewDiff` with their own action names and territory claims. Two functions, each mandatory for its dispatch path, each asserted at the dispatch seam.

### 4.7 The contract snapshot

Every run row (builder `phase_run`, guardian `worker_run`, §4.5) records an immutable **contract snapshot** at dispatch: CLI version (`claude --version` output), fully resolved model id (never an alias; the dispatch resolves `fable`/`sonnet` to the concrete id and records it), effort, the argv hash beside the complete argv in the durable run dir, prompt hash, generated-settings hash, tool contract (allowed and disallowed tools, agents hash), max turns, max budget USD, and sandbox canary id; the builder's row additionally records the registry snapshot hash (§1.5), which guardian runs do not have. **Every retry and resume of that phase reuses the snapshot verbatim** under a new `phase_run.attempt`; it never re-resolves from the live profile, CLI, or alias. **A changed environment never changes a running task by itself.** At every dispatch the builder compares the snapshot it is about to reuse against the live environment (CLI version, resolved model id, profile hash, registry version, agents hash) and records any difference as `contract.drift` on the run row; drift is reported by `reeve task why`, `show`, and doctor, and the attempt still runs under the snapshot. Adopting the drift is a founder command, `reeve task regenerate <id>`: it bumps the generation with a `task.contract_changed` event (§3.2), re-resolves the registry and the contract, and re-enters the task at **SPEC_DRAFT** if it is past GATE (the spec is re-rendered under the new contract and goes through the full gate again as a new head) or at its current phase otherwise (a fresh attempt under the new snapshot). No CLI upgrade, profile edit, or alias change can move a task without that command.

### 4.8 Resume through the seam; no optional safety parameter

`--settings` does not survive `--resume`, and `workerArgs` today defaults `settings` to null: a naive resume would relaunch a worker with no sandbox at all, the exact optional-safety-parameter class this design exists to remove. So every resume dispatch rebuilds the complete argv from the contract snapshot (settings, tools, agents, model, turns, budget, schema), re-validates the settings, and `workerArgs` **hard-fails, not defaults**, when any action passes no settings. Builder lanes may use the shipped `lanes[].sensitiveOk` mechanism where a task's territory legitimately sits inside `sensitivePaths` (verbatim claim, per-file exemption scoped to the declaring lane); quarantine and self-governing paths remain unreachable by any declaration. Test: a resumed worker's argv equals the original attempt's snapshot argv byte for byte except the session id.

## 5. The depth classifier

`BUILD_SIZE` emits `sizing.json`: `{depth: trivial|standard|deep, est_files, est_weighted_files, est_packages, est_slices, risk_paths_touched, rationale}`.

**Deterministic floors applied by reeve after the worker** (the model proposes, code disposes): territory intersects profile risk paths, minimum `standard`; territory spans more than `builder.budget.maxPackages` packages (default 2) or `est_weighted_files` exceeds the reviewability budget (§8.2, default 10), minimum `standard` and `est_slices >= 2`; `scout-*` verification tasks may be `trivial`. Floors are code and are listed in the spec so the founder sees which fired. Territory always exists by this point (§2.2), so the floors always have something to intersect.

Depth drives research and design budgets and fan-out width (§6), whether RESEARCH runs at all, and spec length expectations. At `trivial` depth the machine takes the explicit `SIZING → DESIGN` edge (§3.1), recording a `research.skipped` event: DESIGN is dispatched directly, its prompt requires a short "measured context" section at the top of `design.md` standing in for the absent `research.md`, and `reviewArtifact`'s expectations adjust by depth. **No depth skips the gate**: trivial shrinks phases and shortens the spec; the spec PR always exists.

**Visible and overridable, with a defined transition for every phase** (edges in §3.1): `sizing.json` renders as the spec PR's "Sizing" section, floors included, with the line: "Override: comment `/reeve depth <level>` on this PR, or run `reeve task depth <id> <level>`." The comment path accepts only the founder's numeric GitHub user id, which comes from the profile key `builder.founder.userId` (in FIELDS, with `builder.founder.login` as the snapshot; `reeve builder doctor` resolves the login to the id once and refuses to run the builder if they disagree) and is copied into every task's registry snapshot as `founder_user_id` (§1.5, §11.2). Login snapshot today: `mobeenabdullah`, the sole gh identity on this machine. Every accepted override is recorded as a durable `sizing.overridden` event before anything acts on it:

- **During SIZING, RESEARCH, or DESIGN**: the current phase is re-dispatched (same phase, new attempt; the generation is unchanged because nothing is bound before APPROVED, §3.2) with the new depth's budgets and fan-out width.
- **During SPEC_DRAFT, SPEC_PR_OPEN, or GATE**: the task takes the explicit backward edge to **DESIGN**. During GATE the comment is first a founder event under §7.3: it **stops the 15-minute clock and never counts as silence**; it is the single non-approval founder event reeve fully classifies, so instead of the `founder-unclassified` hold it takes this GATE → DESIGN edge; the pending gate decision is void with the window, and the next spec push mints a new gate_request.
- **After APPROVED** (IMPLEMENTING onward): never automatic. The override is recorded, the task moves to **BLOCKED** with escalation `bt:<id>:depth:post-approval`, and the founder chooses the exit (§3.4): `reeve task resume <id>` continues as approved (generation and approval unchanged; the override stays recorded but inert), or `reeve task resume <id> --redesign` re-enters DESIGN at the new depth (generation bumps), closing any open slice PR; the new design goes through the full gate again.

**Floors versus overrides**: the floors bind the classifier's proposal, never the founder. A founder override always wins, but the acknowledgment notification names any floor the override crossed. No override skips the gate at any depth.

## 6. Research and design: fan-out inside one worker

reeve never orchestrates multi-agent workflows. Fan-out is Claude's own subagent machinery, which works under `-p`:

- Workers launch with `--agents <json>` carrying purpose-built subagent definitions (measurer, prior-art-scout, adversarial-critic, judge): explicit definitions, versioned in reeve, hashed into the contract snapshot (§4.7), identical in any cwd; no dependence on `.claude/agents/` discovery or on `--settings` surviving resume.
- `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` set to the phase budget so background subagents are not killed at the 10-minute default. Nesting stays within the default 3 layers. Subagents inherit the worker's sandbox; they have no more authority than the worker.
- **Fan-out is for measurement, not decisions**: parallel researchers gather facts; the single main agent writes the artifact and makes every design choice. Judge-panel fan-out only scores alternatives the main agent enumerated. Depth sets width: trivial none, standard up to 3 subagents, deep up to 6 plus one adversarial-critic pass whose findings are input to the lead, never a gate; the real gate is the spec PR.
- Artifacts: `research.md` (facts with command-and-output evidence, file:line citations) and `design.md` (chosen approach; alternatives rejected with reasons; **ordered slice list**: each slice has a title, expected files with their weighted count against the reviewability budget, packages touched, an atomicity exception with justification where the budget is exceeded (§8.2), test plan, and a machine-checkable done-condition). Both land in the artifacts dir (durable before transition) and are committed to the spec branch so the founder reads them rendered next to the spec, and so the approved head SHA pins them (§8.1 reads them back from that SHA, never from the local dir).
- For ledger tasks (after S5), RESEARCH also writes `OPS/research/reeve-bt-<id>.md` plus the real `research:` node and `DEPENDS_ON` link through the typed CLI, closing the loop opened at claim time.

## 7. The spec PR and the gate

This section encodes the founder's gate revision of 2026-08-21, with one refinement flagged in §7.3: the 15 minutes are measured from the moment the founder was demonstrably told, which in the normal case equals the Codex timestamp within seconds.

### 7.1 Host and mechanics

- **Host: `nextlyhq/nextly-ops`**, private by design (Rule 15), the ledger's own home, covered by the Codex connector's installation (selection=all). **Prerequisite satisfied**: the founder added nextly-ops to App installation 155196718 on 2026-08-21, verified by probe the same hour (the App reaches nextlyhq/nextly and nextlyhq/nextly-ops, and the installation token carries contents:write, pull_requests:write, issues:write, checks:write). `reeve builder doctor` keeps asserting it, and the escalation `builder:app-install:<repo>` exists for any future spec-repo configuration whose install is missing. Per-project `specRepo` override exists for future revnix projects (revnix needs a fresh App installation). The task's registry snapshot records the spec repository's numeric id (§1.5); `gate_request` and `approval` are keyed by it (§11.2), because PR 12 exists in every repository.
- The spec worktree lives in the dedicated spec clone under `~/.reeve/clones/<project>-spec/` (§1.8), never the ledger clone and never the founder's workspace.
- Branch `reeve/spec/bt-<id>` (the spec repo is private, so the name is permitted; the Rule-15 lint would refuse it on any non-private target), files `specs/bt-<id>/{spec.md, sizing.json, research.md, design.md}`. Push and `gh pr create` are **hub outbox effects with the App installation token**, never a worker grant, each preceded by the §1.7 visibility re-query. Then `gh.review.request` for Codex **plus** the trigger comment (standing rule: trigger Codex on every new PR and every push).
- Every reader of Codex matches the REST login **`chatgpt-codex-connector[bot]`** by numeric user id with the login as snapshot, and reads **both endpoints**: findings arrive as review objects; clean passes and quota refusals arrive only as issue comments.
- CodeRabbit is **optional and advisory** on spec PRs: reeve may fold a useful CodeRabbit finding into a revision, but CodeRabbit's silence never blocks, its findings never force a revision by themselves, and its clean never approves anything.

### 7.2 Spec template (plain language; the founder reads this)

`spec.md`, sections in order: **What and why** (two plain paragraphs; task provenance and ledger links) · **Sizing** (classifier JSON, floors, override instructions) · **Current behaviour** (measured, with commands) · **Proposed behaviour** (concrete before/after examples) · **Slices** (steps, files with weighted count, packages, atomicity exception if any, tests, done-condition each) · **What we will NOT do** · **How we'll know it worked** (machine-checkable commands per planned PR) · **References** · **Approval instructions**: how to approve, in the committed file; where to find the SHA, everywhere else. A committed file cannot contain the SHA of the commit it is part of, so `spec.md` never carries a head SHA: it says "To approve: approve this PR review, or run `reeve task go bt:<id> --sha <prefix>`, copying the prefix from this PR's description or from the notification. Approval binds to exactly the revision you are reading." The live prefix lives in the **PR description body**, an API-editable surface outside any commit, refreshed by the same outbox effect that pushes each revision (idempotency-keyed with the push), and in every notification.

### 7.3 The gate state machine (Codex is a mandatory serial witness; head-SHA-bound; notice-receipted)

**Revision cap: 10 rounds** (founder, 2026-08-22; was 5). Measured on
revnix/reeve #4, which took **8 rounds and 43 genuine findings** before the
character of the findings changed from new areas to follow-ups on its own
fixes. A cap of 5 would have escalated that PR mid-flight with real defects
still open, including two privilege-escalation paths found in rounds 5 and 6.
Ten is the observed ceiling plus headroom, not a guess; a task that reaches it
is genuinely stuck and belongs with a human.

The rule, in the founder's own framing: every spec PR must first be clean by Codex. Codex never says "approved"; it keeps reviewing until it finds nothing, and the comment saying it found no issues is the go-ahead from Codex. Only after that does the founder's 15-minute window start. If the founder approves, the task proceeds immediately; if the founder objects, reeve revises; if the founder says nothing for 15 minutes after the Codex clean pass, reeve proceeds.

**The refinement, stated plainly.** GitHub's timestamp proves when Codex spoke, not when the founder was told. If the builder was down for 20 minutes, observed an old clean comment on restart, or the notification failed, "15 minutes after Codex" would be 15 minutes the founder never had. So the silence window is measured from **`max(clean_created_at, notice_delivered_at)`**: the later of Codex's comment and the durable delivery receipt of reeve's notice to the founder. In the normal case the notice goes out within seconds of the comment and the two clocks coincide; the refinement changes nothing then. When they differ, safety wins the small timing disagreement.

**Durable rows.** `gate_request(task, spec_repo_id, spec_pr, head_sha, round, task_generation, requested_at)`, keyed `(spec_repo_id, spec_pr, head_sha)`: one per pushed revision, so binding is structural; a decision on revision 1 physically cannot attach to revision 3. `approval(task, spec_repo_id, spec_pr, head_sha, actor_id, actor_login_snapshot, kind, verdict, observed_at, source_id, task_generation, superseded_at, superseded_by)` records founder approvals, Codex clean passes (actor the connector's numeric id, kind `codex_clean`, source_id the comment id), and **silence approvals** (kind `founder_silence`, actor the founder's numeric id, source_id `silence:<clean_source_id>`, `receipt_ref` the notice receipt that started the window), so every grant is independently replayable forever. A CLI-path approval additionally records `command_line` and `head_read_at`. A GitHub-review approval's `source_id` is the review id; a CLI-path approval (`reeve task go`) mints its own durable one, `cli:<ulid>`, recorded with the invoked command line and the timestamp of the live head re-read the command performed. `notice_receipt(task, head_sha, clean_source_id, channel, kind, delivered_at, receipt_ref)` records the delivery of the clean notice (kind `delivered`, with the channel's own delivery identifier) or an explicit founder acknowledgment (kind `founder_ack`, from `reeve task ack <id> --sha <prefix>` or a reaction on the notice). An acknowledgment is always of a specific clean pass: `reeve task ack` refuses with "no Codex clean pass at this head yet; nothing to acknowledge" when no clean-pass row exists for the head, so every receipt row has a real `clean_source_id` and the key `(task, head_sha, clean_source_id)` always resolves. All timestamps are **GitHub's** (`created_at`/`submitted_at`/Date header) for GitHub events and the **delivery channel's** for receipts, never the local clock (local calendar is PKT, a measured failure).

**The clean notice is an outbox effect, not a side thought.** When the matcher below classifies a clean pass at head H with source id S, the same tx enqueues `gate.clean_notice` keyed `(task, H, S)`. Its executor sends the notification through `notify.mjs`, which already requires **every configured channel** to succeed before it reports success; the settle writes the `notice_receipt` row only on that all-channels success, with each channel's own reference joined into `receipt_ref`. **What a qualifying reference is, per channel**: the ntfy publish returns HTTP 200 with a message id (that id is the reference; the server accepted every push to date, so receipts are producible on day one); the macOS desktop channel has no server, so its reference is `desktop:<iso-timestamp>` on a successful `osascript` exit (the same rule applies to `notify-send` and the Windows toast on their platforms). A channel that returns neither a success response nor an exit status cannot qualify and fails the delivery; `notify.mjs` gains the return of channel references for this (§11.5). Delivery failure retries under the outbox's backoff; delivery **UNKNOWN** (no confirmation either way) leaves the task in GATE with no silence eligibility and escalates `bt:<id>:gate:notice-unknown`. **Notice is never inferred from enqueue.** The founder can always short-circuit an undelivered notice by approving or by `reeve task ack`, which writes a `founder_ack` receipt.

**Gate results and states.** WAIT and HOLD are results, not states: the task remains in **GATE** with the named escalation standing, re-evaluated each tick. Exactly two gate outcomes leave GATE without APPROVED or a revision: the revision cap (row 1, ten distinct rounds) moves the task to **ESCALATED** (held, §3.4; a founder resume re-enters GATE with the round counter reset), and a founder `/reeve depth` comment takes the GATE → DESIGN edge (§5).

**The Codex clean-pass matcher is a strict grammar, not a heuristic.** Measured live 2026-08-21 on nextlyhq/nextly #1129 and #1130: a clean pass is an **issue comment** by `chatgpt-codex-connector[bot]` whose body matches the template "Codex Review: Didn't find any major issues." followed by a sign-off ("Hooray!" and "Delightful!" both observed), and which contains the line "**Reviewed commit:** `<10-hex>`". The named reviewed commit must **prefix-match the current head**. A refusal never names a reviewed commit, which is the structural tell that separates the two. **Anything that does not match the strict grammar is NOT a clean pass.** The matcher fails closed: an unmatched comment classifies as Codex-silent and the task WAITs. Phrasing drift degrades to safety, and `reeve builder doctor` surfaces a repo where requests go out but nothing ever matches. A review object with findings covering the head always disqualifies the comment path for that head. The matcher's fixtures are the live #1129/#1130 corpus plus refusal and partial-scan negatives.

**Founder events.** If the founder-event projection for the spec PR is **incomplete** (a pagination that did not finish, §7.6), founder events read UNKNOWN, and UNKNOWN is handled exactly like HOLD (the task stays in GATE, the window does not advance); an incomplete page is never counted as zero events. Silence is scoped to the **current head**: it means **ZERO founder events of any kind on the spec PR since the current head's `gate_request` was minted** (an early free-text comment on revision 1 does not disable the silence path on revision 3; a push voids the window and starts a fresh count), where the events are: reviews, issue comments, inline comments, review dismissals, and `/reeve depth` overrides all count, read from the inbox (§7.6) with GitHub timestamps and matched by the founder's numeric user id. Any founder event that is not a SHA-bound approval and not an explicit changes-request **stops the clock**. Exactly one is classified with defined handling: a `/reeve depth <level>` comment, which after stopping the clock takes the GATE → DESIGN edge per §5. Every other non-approval founder event holds the task and escalates `bt:<id>:gate:founder-unclassified`. Test: founder free-text comment plus Codex clean pass still leaves the task in GATE; founder depth-override comment plus Codex clean pass lands the task in DESIGN, never APPROVED.

**The decision table.** Each builder tick, for a task in GATE: pin `head_sha`, classify Codex at that head (strict grammar, both endpoints, sha-prefix coverage), read the notice receipt for (task, head, clean source), read all founder events. **Founder events are evaluated in GitHub-timestamp order, and the most recent explicit decision governs**: a changes-request that arrives after an approval supersedes that approval for the head (the approval row stays as history with `superseded_at` set and authorizes nothing), and an approval that arrives after a changes-request stands, becoming APPROVED only if Codex is clean at the head. Rows 2 and 3 below are therefore read against the **latest** explicit founder decision, never the first one found. First matching row wins:

| # | Codex at current head | Notice | Founder | Result |
|---|---|---|---|---|
| 1 | Findings (review objects covering head) | any | any | **REVISE** (GATE → SPEC_DRAFT): push revision, re-request Codex, mint the next gate_request; loop until clean. Revision cap: **10** distinct rounds, then ESCALATED with `bt:<id>:gate:revision-loop` |
| 2 | Clean pass naming this head | any | Latest explicit decision is an approval bound to this head (review `commit_id`, or `reeve task go --sha`), with no later changes-request on this head, whenever it arrives | **APPROVED** immediately (path: codex-clean plus founder) |
| 3 | Clean pass naming this head | any | Latest explicit decision requests changes (review or explicit changes comment); any earlier approval for this head is superseded | **REVISE** (GATE → SPEC_DRAFT) |
| 4 | Clean pass naming this head | any | Any other founder event reeve cannot classify (a `/reeve depth` comment instead takes its GATE → DESIGN handling) | **HOLD**: clock stopped, escalate `bt:<id>:gate:founder-unclassified`, wait for an explicit approval or changes-request |
| 5 | Clean pass naming this head | **Receipt exists** (delivered or founder_ack) | Zero founder events for **15 minutes**, measured from `max(clean_created_at, notice_delivered_at)`, and the clean still covers the current head for that whole window | **APPROVED** (path: codex-clean plus founder-silence; written as an approval row of kind `founder_silence` carrying the clean-pass comment id and the receipt ref) |
| 6 | Clean pass naming this head | **No receipt** (pending, failed, or UNKNOWN delivery) | Zero founder events | **WAIT**: no silence eligibility; retry delivery through the outbox; escalate `bt:<id>:gate:notice-unknown` when delivery is UNKNOWN past `builder.gate.noticeMinutes` (default 10) |
| 7 | **Unavailable at this head**: a refusal comment observed after reeve's request, or no Codex response of any kind (no findings, no clean, no refusal) within `builder.gate.codexUnavailableMinutes` (default 60, the re-request window) of the request | any | Latest explicit decision is a SHA-bound approval (review `commit_id` or `reeve task go --sha`) | **APPROVED** (path: founder, codex-unavailable). Founder ruling of 2026-08-21: "if Codex is not available, human approval will be enough." The approval row records the unavailability evidence (the refusal comment id, or the request timestamp and the window) beside the founder's source id |
| 8 | Silent but still inside the window, or clean only for an OLDER head | any | any | **WAIT**: re-request review (outbox, idempotency-keyed per head) at `builder.gate.rerequestMinutes` (default 60), escalate `bt:<id>:gate:unreviewed` at `escalateMinutes` (default 120), hold forever. **Never proceed on silence.** A SHA-bound founder approval observed here is recorded and takes effect at row 2 the instant Codex cleans, or at row 7 the instant the window lapses; a founder **changes-request** observed here triggers **REVISE immediately** (GATE → SPEC_DRAFT). Expect this row often: Codex refused 79% of requests this week |

The table is total: every combination of Codex state (findings, clean at head, unavailable, silent-within-window, stale) and founder state falls into exactly one row. **The unavailability window is measured from the first review request at this head**; re-requests at `rerequestMinutes` are retries inside it and never reset it, so with the defaults a founder approval on a head Codex has ignored for 60 minutes advances at row 7 at the same moment the first re-request goes out.

**Properties that hold by construction:**

- **Codex clean is a mandatory serial witness whenever Codex is available, and the founder's explicit approval stands in for it when Codex is demonstrably not.** There are exactly two paths to APPROVED: a strict-grammar clean pass at the current head (rows 2 and 5), or Codex unavailable at the current head plus a SHA-bound founder approval (row 7). **Founder silence never advances a task without a clean pass**; unavailability widens only what the founder's explicit approval can do, never what silence does. A founder approval while Codex is still within its response window is recorded and takes effect the instant Codex cleans (row 2) or the window lapses (row 7).
- **The 15-minute window belongs to the delivered clean notice**: it starts at the later of Codex's timestamp and the receipt, and runs only while the clean covers the current head. Any push voids the window and every pending decision; the new revision mints a new gate_request, a new notice, and a new receipt.
- Approval bindings, each its own test: an approval row whose `head_sha` does not match the current head authorizes nothing; an approval row whose `task_generation` is older than the task's current generation authorizes nothing (`--redesign` or `regenerate` starts a new contract epoch and re-reads the spec; a depth override, retries, and plain resumes never change the generation, §3.2, so they never void an approval); a superseded approval row (a later changes-request on the same head) authorizes nothing; the founder's approval SHA comes from the review's own `commit_id`, never `headRefOid` (which reports the merged head, a measured gh trap).
- **The silence path never fires on a founder who was never told the clock started**, and "told" is a receipt, not an enqueue.
- **Armed from day one (founder ruling, 2026-08-21).** Row 5 is live from the first spec PR the gate ever handles, at S4. There is no shadow period, no calibration-only posture, and no stage at which advances after GATE must be founder-explicit; the strict measured grammar, the head-SHA binding, and the delivery receipt are the safeguards, and they are in force from the first task. "Supervised pilot" (§0, §9.1) means exactly one thing, human or code-owner approval retained on **implementation** PRs, and it never touches this gate. The audit's recommendation to keep every advance after GATE founder-explicit during calibration was not adopted, because it contradicts this ruling (Appendix B).
- **There is no waiver flag.** The earlier drafts designed an emergency `--waive-codex` path; the founder's ruling replaced it: when Codex is unavailable the founder's ordinary SHA-bound approval is sufficient (row 7), so a Codex-dead spec repo is not a halted builder, it is a builder that waits for the founder. No special command, no waiver row, no second exception exists.

### 7.4 `reeve task go`: SHA required, always

Row 1 can revise the spec **without founder involvement**, so the head can move between the founder reading the spec in a browser and typing `go` in a terminal. Therefore `reeve task go <id> --sha <prefix>` **requires the prefix**: go re-reads the current head from the API, compares, and refuses on mismatch with "spec has moved, re-read: <url> <new sha prefix>". A bare `go` always refuses and prints the current head and the instruction. The prefix is in every notification and in the PR description body; it is never inside the committed spec files (§7.2). An approval means a human read this exact revision, not merely that a SHA got bound.

### 7.5 After the gate: the spec PR stays live

APPROVED does not end reeve's reading of the spec PR. For every non-terminal task past GATE, a **post-GATE spec-PR watcher** runs each tick over the inbox: a founder CHANGES_REQUESTED, a review dismissal, or any new founder comment on the spec PR moves the task to **BLOCKED** with escalation `bt:<id>:spec:reopened` (exit via `reeve task resume [--redesign]`, §3.4), writes a `pr_hold` row for any open slice PR in the same tx (§9.6; the guardian's verdict renders BLOCK from it), and the merge coordinator independently re-checks it (§9.3 clause B4). The founder acting on exactly the artifact reeve called the control surface must always work, at any hour, without knowing any CLI command.

### 7.6 Evidence ingestion: one inbox, not parallel readers

Every external fact the gate, the watcher, and the merge coordinator read (reviews, issue comments, inline comments, dismissals, check runs, PR state) enters through the **existing durable generation-aware inbox** and projection layer, extended to the spec repo and to builder PRs: each row carries external id, generation, content hash, actor numeric id and login snapshot, head SHA, server timestamp, completeness (pagination finished or not), and payload hash. No gate reader paginates GitHub on its own. The fetcher uses conditional requests (ETags), a **serial request queue per installation within each process** (the builder and each guardian daemon hold their own queue; GitHub quota is not coordinated across processes, both honour `Retry-After` and secondary-limit responses, and the provider scheduler of §10.4 covers model quota only), stable pagination, and honours `Retry-After`; an incomplete page marks the projection incomplete, and an incomplete projection reads as UNKNOWN to every consumer. **Polling is the v1 transport.** The adapter is webhook-ready: the same inbox accepts deliveries with signature verification and `X-GitHub-Delivery` dedup when a reachable receiver exists; enabling that is a later switch, not a redesign.

## 8. Implementation

### 8.1 Worktrees and the approved plan

- **One worktree per (task, slice)** under the project's worktreeRoot, via the existing `acquireWorktree`, deliberately disjoint from the guardian's per-PR worktree namespace so the two machines can never collide on a directory. The worker contract of §4 applies in full: credential-less environment, OS sandbox, no network, pre-push hook, bogus pushurl.
- **The plan is read at the approved SHA, never from local artifacts.** A revision loop edits `design.md` in the spec worktree, so the local artifacts-dir copy can be stale relative to what the founder and Codex approved. IMPLEMENT (and the slice cursor logic) materializes `spec.md` and `design.md` via `git show <approved_spec_head>:specs/bt-<id>/design.md` in the dedicated spec clone: the exact bytes at the approved SHA. The sha256 of the materialized slice text is recorded in the phase_event, so the built plan is provably the approved one.
- Worker input: the materialized spec and slice k verbatim, the approved spec head SHA, the gate commands it may run, and the hard rules: this slice only; stay within the slice's declared files and the reviewability budget; lint and build must pass before declaring OK; BLOCKED or INFEASIBLE with a reason is a success outcome.

### 8.2 Territory and the reviewability budget

- **Acceptance is reeve's, not the worker's**: `reviewDiff` compares the actual diff, **including rename source and destination**, against the task's territory claims union the slice's declared files, in the same normalized representation as the claims (§10.1). Sensitive, quarantine, and self-governing path refusal applies as shipped (with `lanes[].sensitiveOk` honored where declared).
- **The reviewability budget is a default, not a universal invariant.** Default target: at most 10 **weighted** changed files per slice, where weights come from `builder.budget.weights` (defaults: source 1.0; tests 0.5; migrations 0.5; generated files, lockfiles, and snapshots 0.25; classification by profile-declared patterns), plus a stronger limit on conceptual surface: at most `builder.budget.maxPackages` packages touched (default 2). **A slice found over budget during IMPLEMENTING is not a spec revision and never becomes a bigger PR**: the split was wrong, which is a founder decision after APPROVED (§5). The task goes to **BLOCKED** with `held_from=IMPLEMENTING` and escalation `bt:<id>:impl:over-budget`; no PR is opened. The founder exits with `reeve task resume <id>` (retry the slice once with the same plan, in case the overrun was the worker's doing) or `reeve task resume <id> --redesign` (re-slice through the full gate as a new contract epoch). There is no IMPLEMENTING → SPEC_DRAFT edge (§3.1).
- **The atomicity exception.** Some changes are one atomic unit that legitimately exceeds the budget (schema plus migration plus generated types plus tests). DESIGN must declare the exception per slice in `design.md` with a justification; it renders in the spec's Slices section; founder approval of the spec approves the exception. `reviewDiff` reads the approved exception from the materialized design (§8.1) and enforces the declared file list exactly instead of the default budget. An undeclared overrun takes the same BLOCKED path as any over-budget slice; a declared exception never widens the territory.

### 8.3 Gate definitions the worker cannot author; controller-run gates

Both reeve's gate re-run and CI resolve through files an IMPLEMENT worker could otherwise modify. Instead of a fixed denylist (which misses Makefiles, task scripts, tsconfig, ESLint configs, Dockerfiles, custom CI scripts), each buildable unit's profile declares **required, validated `gateDefinitionPaths`** (the profile validator refuses a buildable unit without them): package.json script blocks, test runner configs, turbo.json, workflow files, husky hooks, lint and TypeScript configs, container files, and whatever else grades that unit. At admission the builder hashes those paths at the task's base and stores the **gate-definition hash** on the task (§1.5); at each slice start it re-hashes at the approved base.

- **Any worker change to a gate-definition path is a human-only path**: `reviewDiff` escalates `bt:<id>:impl:harness-touched`, and the slice holds in BLOCKED with `held_from=IMPLEMENTING`. **The held diff is preserved, not discarded**: before the hold commits, the controller writes the worker's full diff against the approved base as a durable patch artifact (`~/.reeve/tasks/<bt>/artifacts/impl-g<generation>-s<k>.patch`, tmp+rename+fsync) and records its sha256 on the hold; the worktree itself may be released like any other. The merge coordinator refuses any PR whose diff touches those paths until a `harness_acceptance(task, generation, slice, diff_hash, actor_id, accepted_at)` row exists for exactly that diff's hash. **The only writer of that row is `reeve task resume <id> --accept-harness <hash-prefix>`** (§3.4): it refuses a prefix that does not match the preserved patch's hash and records the full hash, the actor, and the timestamp. The resumed IMPLEMENTING slice then runs in **accepted-patch mode**: no worker is dispatched; the controller re-verifies the patch's hash, applies it to a fresh worktree at the approved base, re-runs `reviewDiff` and the controller-run gates below, and commits it (§8.4). The PR's diff against the approved base is therefore byte-identical to the accepted patch, and clause B7 of §9.3 reads the `harness_acceptance` row against the PR's diff hash and nothing else. Lockfile-only changes are not gate definitions.
- **Gates run through a controller-owned wrapper** (`src/build/gates.mjs`), never by trusting the worker's run: the wrapper checks out the base revision's gate definitions over the worker's source where feasible, runs each command with the controller's environment, and records a `gate_run` row per command: base definition hashes, command, tool versions (node, pnpm, the runner), environment hash, exit code, output hash, and the durable output path. A gate that cannot run records UNKNOWN, and UNKNOWN is not acceptance.

### 8.4 Controller-created commit

The worker leaves a **reviewed diff**, not a git object. After `reviewDiff` and the controller-run gates pass, the **controller** stages exactly the accepted paths (`git add -- <paths>`; nothing else in the worktree is staged, untracked leftovers are discarded), and creates a neutral deterministic commit: author and committer `merge-policy[bot] <{bot-user-id}+merge-policy[bot]@users.noreply.github.com>` (the App's own bot user, whose numeric id is read from the API once and stored in the registry snapshot; a GitHub-attributed identity, so the live ruleset's extra approval for unattributed changes does not fire, verified on a live PR in S7), a sanitized Conventional Commits message derived from the slice title (`<type>(<scope>): <slice title>`, lowercase, 72 chars, lint-checked by the Rule-15 lint of §1.7), no trailers from the worker, no signing key from any ambient config. The commit's SHA is the **attested first SHA** of the slice (§8.5): an output of the trusted boundary, not of the model. A worker that created commits of its own sees them discarded; only the tree matters.

### 8.5 Publication and the attested head chain (hub pushes, guardian receipts)

- **Neutral naming on the public repo.** Impl branches are `mp/<taskid>-s<k>`, PRs are authored by `merge-policy[bot]`, and PR bodies pass the Rule-15 lint (§1.7): the body names the bound spec SHA and the approval path, and carries no spec-repo URL at all (a private URL would still leak naming). Rule 15 holds on every public artifact the builder produces.
- **Push and PR create are hub outbox effects** behind the `publish-pr` switch (§1.4): `git.push.branch` (expected-remote CAS, idempotency key carries the SHA, App token in the controller subprocess env of the automation clone only) then `gh.pr.create`. The push settle appends an **`attested_push` row** `(task, slice, pr, sha, pusher='builder', source_kind='outbox', source_ref=outbox_key, at)` in the hub; the pr-create settle and the `impl_pr` write are **one hub tx** (a crash between them cannot leave an open PR the hub has never heard of; the reconciler completes both together).
- **Guardian repair pushes settle in the guardian's own DB, and the hub imports them.** When the guardian's FIX_CI or review-thread worker pushes a repair to a builder PR, that push settles through the guardian's own outbox in the guardian's own transaction and appends an immutable receipt to the guardian's append-only `guardian_event` table: `(seq, kind='push.settled', pr, head_before, head_after, outbox_key, at)`. The guardian writes nothing to the hub for this. The builder's **receipt importer** reads `guardian_event` read-only each tick (and on demand at the merge pre-flight), imports each new row into hub `guardian_receipt` keyed **`UNIQUE(repo_id, guardian_event_seq)`**, verifies the claimed SHA against git (the commit is reachable from the PR head and its parent is the previous attested head), and only then appends the corresponding `attested_push` row with `pusher='guardian'`, `source_kind='guardian_event'`, `source_ref=<repo_id>:<seq>`. Delivery is **at-least-once**: re-reading the same seq is inert by the unique key. A receipt that fails verification is recorded `rejected` with the reason and escalates `bt:<id>:chain:receipt-rejected`. **A missing import makes clause B1 UNKNOWN** (§9.3); it never makes the push illegitimate, and the importer recovers it from guardian history on the next tick.
- The merge coordinator (§9.3 B1) verifies the chain from `attested_push` plus git log, so guardian repairs keep builder PRs mergeable while a commit smuggled by anyone else still blocks. The common case (a slice needing one CI fix) does not dead-end on the founder, and the smuggle check does not decay into "head equals head".

### 8.6 Handover to the guardian; VERDICT_WAIT

- Once the PR exists, the guardian daemon for that repo owns observation and repair of it (pin head, publish the `ops/merge-policy` check, FIX_CI with the shipped `flakeAssessment` semantics, work review threads). The builder's live run for the slice **ends at IMPL_PR_OPEN**: it never holds a live run while the guardian holds `pr:<n>`, and it releases the slice worktree; guardian repairs use their own per-PR worktree. The task sits in VERDICT_WAIT, polled read-only.
- **VERDICT_WAIT is never a silent forever.** It is the modal state (Codex refuses 79% of requests, so UNKNOWN verdicts are expected and correct), and fail-closed must not mean fail-quiet: a slice whose VERDICT_WAIT exceeds `builder.verdict.staleBudgetMinutes` escalates `bt:<id>:verdict:stale` (identity only; the body names which witness is absent), and the builder probes the owning guardian daemon's heartbeat row each tick (read-only), escalating `bt:<id>:guardian:dead` when it is not fresh. The derived substate WAITING_FOR_GUARDIAN renders in dash.
- Slices are serial within a task (review-round economics), parallel only across tasks.

## 9. Merge coordination: hub-owned, builder-only, server-enforced

### 9.1 Authority: switches and the server gate

- **Auto-merge in this programme is builder-only.** The merge coordinator lives in the builder process and acts only on PRs bound to a hub `impl_pr` row at the task's current generation. Ordinary PRs keep receiving the guardian's verdict and check runs exactly as today and **never auto-merge**; the guardian's existing `ACTIONS.MERGE` decision continues to be logged and never executed. Ordinary-PR auto-merge is a separate, future authorization with its own design (§16).
- **Repository authority is not the switch.** `authority.policy` and `merge.enforcement` in the profile are already set on the live nextly profile and play no role in builder actuation. The coordinator actuates only when `builder.capabilities.mergeBuilderPr=true` (profile, default false, validated in FIELDS, §1.4) **and** the builder process was started with `--actuate-merges` (the generated service definition carries the flag only at S10). There is no other merge key. With either absent, the coordinator evaluates, writes `merge_decision` rows, and enqueues nothing: dark by construction.
- **The server is the final enforcement point, and the guardian programme owns the flip.** Merge actuation is safe only while the live `protect-main` ruleset requires the `ops/merge-policy` status check **bound to the merge-policy App** as its expected source, so that a check from any other source does not satisfy it. Making that check required on nextly is the **guardian programme's capability-4 flip**: a founder decision taken after the verdict shadow week and documented in TRACKER Programme 1. **The builder never flips it**, on nextly or anywhere else; the ordinary-PR false-block rate that the flip risks is Programme 1's shadow-week question, not this programme's. **S8 depends on that flip having happened** (§14): until the ruleset requires the App-bound check, `builder.capabilities.mergeBuilderPr` cannot be enabled, because clause U4 reads UNKNOWN and `reeve builder doctor` reports "unsafe authority".
- **`repo_gate_state` is written by the loop, reported by doctor.** Every builder tick, for every registry project, the loop refreshes one `repo_gate_state` row (§11.2): whether the ruleset requires the App-bound check (required checks and their bound app id, read from the rulesets API), whether the App is installed there with the expected permission set (the installation probe of §1.8), the ruleset snapshot, and `verified_at`. **No merge is ever attempted against a production repository by any probe**; the only merge probe in the system is the canary probe below. Clause U4 (§9.3) reads that row with a 60-minute freshness bound; a row older than the bound, absent, or showing drift yields UNKNOWN. `reeve builder doctor` only reports the row and classifies drift as unsafe authority; it is not the writer.
- **The live negative probe** runs **only** from `reeve builder doctor --probe-live`, **only** against the profile-allowlisted canary repository `builder.canaryRepo` (a disposable repository, never a production project; doctor refuses any other target), and is independent of the capability switches, which govern production PRs. **The canary repository is watched by no guardian instance and is bound to no task**: the probe touches neither `pr_hold` nor the hub outbox (it has no durable effect to reconcile, it cleans up after itself, and it is a founder-run command, which is why it is the one documented exemption from the outbox rule). Its ruleset mirrors production (the `ops/merge-policy` check required from the merge-policy App). Doctor creates a disposable branch and PR there through the App token directly, then attempts a merge under two states that **must** both be refused by GitHub: first with no `ops/merge-policy` check run at H (nothing publishes on the canary, so the required check is absent), then after doctor itself publishes a **failing** `ops/merge-policy` run at H under the App (permitted only on the canary: doctor refuses to publish a check anywhere else, and the check's own summary names it a probe). Each refusal is recorded as evidence on a `probe_result` payload in `hub_event`; doctor then closes the PR and deletes the branch. It is a go-live gate (§14, S8 and S10); unit tests and dry runs are not this evidence. **A probe that merges anything is a P0 incident**: the builder writes the HALT marker (the existing halt-poll file every dispatch and effect checks, failing closed), escalates `builder:probe:merged`, and stays halted until the founder clears the marker by hand.
- **Pilot posture: supervised autonomy.** The ruleset's human/code-owner approval requirement on implementation PRs is **retained** during the pilot (default chosen, §16). A builder PR therefore merges only after a human approved it on GitHub, the guardian's witnesses passed, and the hub's chain is intact. Removing the human approval is a later founder decision, after server enforcement is live and canary evidence exists.

### 9.2 Kind: a builder PR is a bound PR, and the binding fails closed

A PR is a **builder PR** when a hub `impl_pr(task, generation, slice, repo_id, pr)` row binds it. The coordinator also recognizes **builder-shaped** PRs (head branch `mp/*`, or author is the App) that have no binding: for example after a crash between effects, before the reconciler has caught up. The scan for them has a named source: each tick the coordinator reads the inbox projection (§7.6) of every open PR on every registry project and classifies each by head branch and author; it does not depend on a task being in VERDICT_WAIT. A builder-shaped PR with an incomplete chain (no impl_pr row, no approval row, no attested chain) **never merges** and escalates `bt:unknown:merge:unbound:<repo_id>:<pr>`. "No hub row" is never read as "ordinary PR" for a builder-shaped head; a crash cannot reroute an unapproved PR down any merge path, and in this programme there is no other merge path. Everything that is neither bound nor builder-shaped is an ordinary PR and is out of the coordinator's scope by kind, recorded as such, never evaluated.

### 9.3 Clauses

`mergeEligible(task, slice, pr)` runs in the builder for each task in VERDICT_WAIT, each tick. Every clause names its evidence source; a clause that cannot read its evidence yields UNKNOWN, and UNKNOWN never merges. All clauses are re-evaluated at enqueue time **and** in the pre-flight immediately before the API call (§9.5).

**Witness clauses (evidence from the guardian, GitHub, and the ledger):**

- **U1.** Guardian verdict `PASS` at pinned head H, read from the per-repo guardian DB read-only (7-clause worst-wins; UNKNOWN never PASS). The verdict row's head must equal H exactly.
- **U2.** Live GitHub state agrees at H: the `ops/merge-policy` check run at H is success and its app id is the merge-policy App; CI rollup success (`conclusion == ""` is in-progress, not success); zero unresolved threads; reviewer states clean per the 4-state read; the human/code-owner approval the ruleset requires is present (§9.1); mergeability state is `clean`. Read through the inbox projection (§7.6) and re-read live in the pre-flight.
- **U3.** Zero open ledger BLOCKS edges against `pr:<n>` (ledger-sourced tasks only; out of scope by source kind for founder-filed tasks, recorded as such), **with a stated freshness contract**: a `ledger sync` in the dedicated clone within `builder.merge.ledgerFreshMinutes`, failing to UNKNOWN (never to zero) on sync error, wrong clone, or parse failure, with the sync timestamp recorded in the decision row.
- **U4.** Capability and identity: `builder.capabilities.mergeBuilderPr` is true, the process carries `--actuate-merges`, the App is installed on the repo with the expected permissions (probe; failure escalates `builder:app-install:<repo>`, **never** a founder-token fallback), and the repo's `repo_gate_state` row (written by the builder loop every tick, §9.1, §11.2) shows the ruleset requiring the App-bound check and the App installed with the expected permissions, with `verified_at` no older than `builder.merge.rulesetFreshMinutes` (default 60). An absent, stale, or drifted row is UNKNOWN; doctor reports the row but never writes it.

**Shadow scoring, so dark evaluation proves something.** Every evaluation records two outcomes in the decision row (§9.4): `witness_outcome`, computed from every clause **except** U4's switch sub-clause (the capability switch and the process flag), and `actuation_outcome`, which is `witness_outcome` AND the switches. While the switches are off, `actuation_outcome` is UNKNOWN by design on every row; S9's false-merge metric and the S8 clause matrix are computed over `witness_outcome` (would reeve have merged?) against ground truth, because a metric over `actuation_outcome` during the dark stages would be vacuously zero.

**Builder chain clauses (evidence from the hub):**

- **B1.** **Attested head chain intact**: H equals the latest `attested_push` sha for this (task, slice), and every commit between the controller's first commit (§8.4) and H is covered by attested pushes (builder outbox pushes and imported guardian receipts alike, §8.5), verified from git log plus the hub rows, never from a worker report. A guardian receipt not yet imported makes this clause UNKNOWN, not a refusal. reeve's own repairs merge; anyone else's commit blocks. Companion test: guardian FIX_CI push, receipt imported, PASS, merges; the same with the import withheld stays UNKNOWN; a foreign commit blocks.
- **B2.** **Approval chain valid**: an `approval` row exists for the governing spec head at the task's current generation, (of kind `founder_review`, `founder_cli`, or `founder_silence`) and either a `codex_clean` row (strict grammar, §7.3) exists for that same head, or the approval row's `path` is `founder_codex_unavailable` with its unavailability evidence recorded (§7.3 row 7); the decision row quotes whichever applied.
- **B3.** **Task liveness**: the hub task is in `VERDICT_WAIT(k)` for exactly this slice at the generation the enqueue recorded. CANCELLING, CANCELLED, BLOCKED, LOST, ESCALATED, or anything else blocks; a founder's cancel must stop a PR that is already green (§3.5 closes it and writes `pr_hold`, which the guardian's verdict renders BLOCK, §9.6; this clause is the independent belt).
- **B4.** **No founder-negative event on the spec PR newer than the approval row's `observed_at`** (the merge-boundary half of the post-GATE watcher, §7.5), read from the inbox.
- **B5.** **Review witness non-vacuous**: the guardian verdict's review clause emits PASS on an empty blocking-reviewer roster; for builder PRs that would be absence read as success on the very witness the settled requirement names. So an empty or vacuous roster yields UNKNOWN, and a builder PR merges only with a real external review witness at H (the human approval of §9.1 satisfies it during the pilot), or with an explicit per-project founder acknowledgment recorded as a durable `project_authority(project_id, kind='review-witness', granted_by, until, created_at)` row (§11.2), **written only by `reeve build authority <project> --kind review-witness --until <date>`** (founder-only, §11.6); an expired row (`until` passed) authorizes nothing.
- **B6.** **Ownership fresh (ledger-sourced tasks only)**: the hub's `ownership_check` row shows reeve as projected owner from a full sync no older than `builder.merge.ownershipFreshMinutes` (default 15), and the pre-flight repeats the sync live. Stale, absent, or human-owned yields UNKNOWN and blocks, with `bt:<id>:intake:ownership-lost` standing. Out of scope by source kind for founder-filed tasks, recorded as such.
- **B7.** **Harness untouched**: the builder's controller commit (§8.4) touches no `gateDefinitionPaths` unless a `harness_acceptance` row at this (task, generation, slice) carries exactly that commit's diff hash; the hashes match by construction because the accepted slice commits the preserved patch rather than a re-derived diff (§8.3). Guardian repair commits are judged by the chain (B1) and by the guardian's own diff gate, which from S2 treats the profile's `gateDefinitionPaths` as self-governing for every guardian worker in that repo (a repair that touches one is refused before it is ever pushed), so B7 never has to accept a guardian diff and a repaired builder PR cannot dead-end here.

### 9.4 The merge decision row

Every evaluation, MERGE and refusal alike, writes one durable **`merge_decision`** row in **hub.db**: `(id, task, slice, task_generation, repo_id, pr, head_sha, decided_at, witness_outcome ('MERGE'|'REFUSE'|'UNKNOWN'), actuation_outcome ('MERGE'|'REFUSE'|'UNKNOWN'), clause_results JSON, ledger_sync_at, approval_head_sha, approval_source_id, approval_path, codex_clean_source_id, notice_receipt_ref, server_gate_snapshot JSON, outbox_key, phase ('enqueue'|'preflight'|'settle'))`. `clause_results` names every evaluated clause with its result and evidence reference (guardian verdict row id, inbox row ids, attested_push ids, receipt ids); `server_gate_snapshot` records the ruleset's required checks and the check run's app id as read. `reeve task why` renders the lineage from these rows; the `bt:<id>:merge:refused` escalation body cites the row.

### 9.5 Actuation: one tx, a pre-flight re-read, and a server-side CAS

1. **Enqueue tx**: when every clause is MERGE, the coordinator writes the `merge_decision(phase='enqueue')` row and the outbox row `gh.pr.merge {repo_id, pr, method: profile merge.method, sha: H}` with idempotency key `bt:<id>:g<generation>:VERDICT_WAIT:merge:<H>` (the §3.2 sha-keyed form), `task_id`, `task_generation`, fence, and `cancellable=true`, **in the same hub tx as a guard on the task row**: `UPDATE task SET updated_at=:now WHERE id=:id AND phase='VERDICT_WAIT' AND generation=:g`. The guard is not a bump: the generation is unchanged. Zero rows updated means the task moved under the coordinator's feet, and the tx refuses to enqueue.
2. **Pre-flight, inside the outbox lease and immediately before the API call**: re-read hub task phase and generation (must be VERDICT_WAIT(k) at the recorded generation, not voided, not CANCELLING), re-read the guardian verdict at H, re-read live GitHub at H (PR state, mergeability, check run and its app id, approval state, head equals H), re-run the ledger ownership sync for ledger-sourced tasks, and re-verify the chain including a fresh receipt import pass. Any change settles the row `fenced` with a `merge_decision(phase='preflight', witness_outcome='REFUSE')` row and no call.
3. **The call** uses GitHub's merge endpoint with `sha: H`: the server refuses with 409 when the head no longer matches, so a head that moved between pre-flight and click fails rather than merging the wrong code. Executed with the App installation token, the merge-boundary identity.
4. **Settle only via `reconcilePrMerge`** (`mergedAt` and merge commit from the API), writing `merge_decision(phase='settle')`. An API refusal beyond the clauses (ruleset, approval, 405/409) raises the shipped `ESCALATIONS.PROTECTION_UNMET` with `bt:<id>:merge:refused` standing; nothing is retried blind.

### 9.6 Cancel and reopen versus an in-flight merge

The dangerous ordering is: merge row leased first, cancellation or reopen committed second, API call third. Three independent mechanisms cover it, and the test for each exists because each alone is insufficient:

- **Same transaction domain.** Cancellation (§3.5), reopen (§7.5), and merge intent all live in hub.db; the cancel tx voids the pending merge row or records the in-flight one in `drain_set`, and the pre-flight re-read (§9.5) sees the new phase before the call.
- **`pr_hold`, read by the guardian's verdict: one publisher per check.** The builder **never publishes a check run on a production repository**; the guardian is the sole publisher of `ops/merge-policy` there. The one documented exception is the canary repository (§9.1), which no guardian watches and no task is bound to, where `reeve builder doctor --probe-live` publishes a probe check to exercise the server gate. On CANCELLING, on ESCALATED, and on BLOCKED, the entry tx writes one `pr_hold(id, task, repo_id, pr, head_sha, reason, created_at, cleared_at)` row per open builder PR, with `reason` drawn from the closed set `cancel | reopen | ownership_lost | harness_touched | over_budget | depth_post_approval | escalated | blocked_other` (for `blocked_other` the hold's escalation identity rides in `detail`) in hub.db (§3.2.5, §11.2); `reeve task resume` sets `cleared_at` in its own tx (§3.4). **The guardian's verdict gains exactly one additive clause for builder PRs**: when a PR is structurally a builder PR (head branch `mp/*` or authored by the App, the same detection as §9.2), the guardian reads `pr_hold` from hub.db **read-only** and, if an uncleared row exists for `(repo_id, pr)`, the clause yields BLOCK and the 7-clause worst-wins verdict is BLOCK; the guardian's next `ops/merge-policy` run at H therefore has conclusion `failure`, and because the ruleset requires that check from that App and evaluates the latest run at H, the server refuses a merge even against a stale client request that slipped past everything else. If the hub is unreadable the clause yields UNKNOWN, which is never PASS, so a builder PR cannot go green while the hub is down; ordinary PRs never evaluate the clause. The read is the guardian's second and last hub touch (§1.1, §13): its hub connection allowlist is `provider_lease` and `provider_state` for writes and `SELECT` on `pr_hold` only. The window between the hold write and the guardian's next tick is covered by the first mechanism (the pre-flight re-read) and by the PR close the same compensation enqueues; a reopened PR re-enters only through founder action and a coordinator that refuses it (B3).
- **The server-side sha CAS** covers the head-moved case the other two do not.

Test matrix (S8): merge leased, then cancel, then call: refused at pre-flight; merge leased, pre-flight passed, then cancel committed before the call: the hold row exists, the guardian's next verdict at H renders BLOCK, the server refuses the stale request; founder CHANGES_REQUESTED on the spec PR after enqueue: refused; head moved after pre-flight: 409, row fenced; hub unreadable from the guardian: builder PR verdict UNKNOWN, ordinary PR verdict unchanged.

### 9.7 After merge; FINALIZING

After settle: SLICE_MERGED (witness: the reconciler's `mergedAt`), merged head compared to the latest attested head, then the next slice or FINALIZING. **FINALIZING is a reeve-code phase, not a worker phase**: no claude session runs. It executes the §2.6 ledger write-back through the outbox (ledger-sourced tasks), posts a completion comment on the spec PR linking every merged slice PR and closes it, releases the task's remaining leases and worktrees, and CAS-transitions to DONE only when every enqueued effect has settled through its reconciler. A crash mid-FINALIZING resumes it like any phase: the effects are outbox-deduped and operation-id-keyed, so the write-back happens exactly once.

## 10. Concurrency: N tasks, M projects, one machine

### 10.1 The territory language (v1: canonical path claims only)

"Full glob intersection" is underspecified and deceptively hard (negation, braces, `**`, character classes, renames, symlinks, case, submodules). v1 accepts exactly two claim shapes, and nothing else:

- an **exact file**: `packages/x/src/index.ts`;
- a **recursive directory prefix**: `packages/x` (claims everything below it).

Claims are repository-relative, normalized (no leading `./`, no `..`, no trailing slash, no duplicate separators, NFC, case preserved and compared exactly as git does), and stored as **child rows** `task_territory(task, kind, path)`, never as one TEXT blob. Refused with an example of the accepted grammar: negation, braces, extglobs, character classes, `*`/`**` wildcards, absolute paths, paths that traverse a symlink at claim time, submodule paths. **Overlap** is computed over normalized prefixes: two claims overlap when either is a prefix of the other or they are equal. **Diffs are compared in the same representation**: every changed path, including both the source and destination of a rename, must fall under one of the slice's claims. Tests: rename out of territory refused; symlinked path refused at claim; `packages/x` versus `packages/xy` do not overlap; `packages/x` versus `packages/x/y.ts` do.

### 10.2 Leases

- **Leases live in the hub, and the two kinds have different lifetimes on purpose**: `directory_lease(path, owner_kind, task, pid, lstart, expires_at)` with an absolute-path unique index, covering worktrees (`owner_kind='worktree'`, `task` set) and the shared automation clones of §1.8 (`owner_kind='clone'`, `task` NULL, because a clone belongs to no single task), is **process-scoped**: heartbeat at lease/4, LEASE_SECONDS=120, reaper with pid+lstart grace, the proven ops.mjs machinery, because the thing it protects dies with a process. `territory_lease(project, kind, path, task, expires_at, pinned_until)` is **task-scoped**: granted and released by task transitions and its expiry refreshed by the builder loop's per-task heartbeat. A task is a row, not a process, so "dead" is defined by state: the reaper deletes a territory lease only when its task row is in a terminal state, or in a held state with no live pin. That condition cannot normally arise, because release happens in the same tx as the transition; the reaper is the belt for a row left behind by a migration or a manual edit, and it never reaps a lease whose task is active, whatever its age.
- **Full lifecycle.** Grant happens inside the admission tx for both intake paths identically (§2.2, §2.4.3). Release happens inside every terminal transition's tx (LOST, CANCELLED via CANCELLING, DONE, INFEASIBLE) and on **both held states**, BLOCKED and ESCALATED (§3.4), unless a `--pin-territory` is live; **re-grant on `reeve task resume` runs the identical intersection check**. The intersection is re-run against current ledger claims at each IMPLEMENTING slice start (piggybacking on the §2.5 sync); on a conflict the slice is not dispatched and the task goes to **BLOCKED** with `held_from=IMPLEMENTING` and escalation `bt:<id>:lease:conflict` (the body names the overlapping claim and its owner), exiting through `reeve task resume` once the founder has settled who owns the territory. Skips emit the durable `candidate.skipped` row, and the intake loop raises `bt:<id>:lease:starved` (identity: the HOLDING task) when one task's lease has produced skips across more than `builder.lease.starvedHours` (default 24). Tests: a LOST task's territory is claimable by the next filing; an ESCALATED task's territory is claimable; a pinned ESCALATED task's territory is not, until the pin expires.

### 10.3 Admission

`builder.maxConcurrentTasks` (default 2), max 1 worker per task, at most one IMPLEMENTING slice per project at a time (keeps builder and guardian-FIX_CI worktrees from crowding one repo), the existing load-aware `capacity()` so builder workers yield to machine load, and a **provider lease** (§10.4) for every model dispatch.

### 10.4 The global provider scheduler (the one guardian hub write)

The subscription is the real choke point. Two fable/high IMPLEMENT workers can exhaust the shared claude subscription's rate window; the guardian's serial tick then blocks inside its inline `await` on a rate-limited FIX_CI, freezing verdicts for every PR on that repo. Observation after the fact cannot reserve shared quota or give true priority: two daemons can both observe free capacity and launch before either exit is recorded. So the hub carries a **provider scheduler**, and **both daemons claim it transactionally before any model dispatch**; verdict polling never depends on it.

- `provider_lease(id, owner ('guardian'|'builder'), repo_id, run_ref, pid, lstart, priority, budget_usd, status ('queued'|'held'), requested_at, started_at, heartbeat_at, expires_at)` and `provider_state(provider PRIMARY KEY, concurrency_limit, guardian_reserved, cooldown_until, last_429_at, last_signature)`.
- **Admission rule**, evaluated under `BEGIN IMMEDIATE`: a builder request is admitted only when held leases are below `concurrency_limit` minus `guardian_reserved`, no guardian request is `queued`, and `cooldown_until` has passed. A guardian request is admitted whenever held leases are below `concurrency_limit` and no cooldown is live; when it cannot be admitted it is recorded `queued`, which blocks the next builder admission until it is served. A 429 or rate-limit signature from any worker exit sets `cooldown_until` (backoff from `builder.provider.cooldownSeconds`, default 300) and records the signature; the builder admits nothing while a cooldown is live.
- Leases are heartbeated with the run and **reaped after process death** (pid+lstart liveness plus expiry), so a crashed worker frees its slot. A builder lease may be revoked at a safe phase boundary in favour of a queued guardian request (`builder.provider.preemptAtBoundary`, default true), never mid-phase.
- This is the **one justified guardian hub write**: `src/provider.mjs` is shared, the guardian calls `claimProvider` before FIX_CI and review-thread dispatch and `releaseProvider` on exit, and touches no other hub table (§13).
- **Limits are measured before they are chosen.** Whether headless (print-mode) usage and interactive usage draw from one pool or two is account-specific; S3 (§14) measures it with real phase runs and records the answer in the profile as `builder.provider.concurrencyLimit` and `guardianReserved` with the measurement's date. Defaults until then: limit 2, reserved 1.
- The guardian side gains a rate-limit **fast-fail**: the dispatch path detects the CLI's rate-limit signature and fails the attempt in seconds instead of awaiting the window, so the serial tick is never quota-blocked for hours. S9's latency proof includes a quota-exhausted trial, not just a loaded-machine one.

### 10.5 The builder tick; multi-project

- **The builder tick never blocks**: phase workers spawn detached (pid+lstart recorded via the fail-closed `onSpawn`); the tick polls run rows in the DB rather than awaiting; liveness is counted from rows, not a variable, so the guardian's `ctx.running` bug is not inherited.
- **Multi-project**: phases carry their project's profile and checkout explicitly from the task's registry snapshot rather than deriving from a watched repo. Filing against a repo with no guardian instance is refused at filing time with a clear message: refuse rather than default.

### 11.4 Backup and restore (part of the hub PR, S2)

- `backup.mjs` discovers `~/.reeve/state/hub.db` and labels its snapshots `hub` separately from owner/repo stores.
- Snapshots via `VACUUM INTO`, followed by `PRAGMA integrity_check` and a `schema_version` read that must match the running binary's expected version; a snapshot failing either is deleted and `builder:backup:failed` escalates.
- Restore validates a hub snapshot by `hub_event` (the append-only table) plus `schema_version`; it **refuses while any writer is live**: the singleton lease row is held by a live pid+lstart, any guardian holds a provider lease, or any `writer_lease` row (§11.2; taken by every hub-writing CLI command for its duration) is held by a live pid+lstart; it prints the holder. Restore itself takes the `maintenance_lock` exclusively first, and every writer, daemon and CLI alike, refuses to begin a write while that lock is held, so a command started a moment after the check cannot slip in.
- **`hub_event` is appended by every authority-bearing write, not only by phase transitions.** §3.2.2 covers transitions; in addition, every tx that writes an `approval`, `gate_request`, `notice_receipt`, `impl_pr`, `attested_push`, `guardian_receipt`, `harness_acceptance`, `gate_run`, `pr_hold` (create or clear), `hold_reason`, `project_authority`, `merge_decision`, a territory or singleton lease grant or release, or an outbox enqueue, void, fence, or settle, appends one kind-named `hub_event` row in that same tx. The projection is therefore replayable from `hub_event` plus artifacts and external receipts, and the **destructive restore drill** has a defined comparison set: drop the live hub, restore the last snapshot, replay, and compare `task` (phase and generation), `approval`, `gate_request`, `notice_receipt`, `impl_pr`, `attested_push`, `harness_acceptance`, `gate_run`, `pr_hold`, `hold_reason`, `project_authority`, `outbox`, `territory_lease`, and `merge_decision` row for row against the pre-drop export. It is an acceptance test of the S2 PR and runs in CI. Process-scoped rows (`directory_lease`, `provider_lease`, `singleton_lease`, `writer_lease`, `maintenance_lock`) are excluded from the comparison by design: they describe processes that no longer exist after a restore. A `maintenance_lock` left by a crashed restore is reaped like any lease: the next writer finds its pid+lstart dead and clears it.
- `reeve builder doctor` reports snapshot age, last integrity result, and restore compatibility of the newest snapshot.
- An **encrypted off-device copy** with retention is a requirement of this design; its destination is a founder decision listed in §16.

### 11.7 Escalations: two-field, enforced

For every builder subject, the escalation Map key is the **bare identity** and the report rides only in the alert body; a test asserts no builder `escalations.set` call interpolates variable detail into the key. Identities, each with a named producer: `bt:<id>:gate:unreviewed` (§7.3 row 8), `bt:<id>:gate:revision-loop` (row 1), `bt:<id>:gate:founder-unclassified` (row 4), `bt:<id>:gate:notice-unknown` (row 6), `bt:<id>:spec:reopened` (§7.5), `bt:<id>:spec:visibility` (§1.7), `bt:<id>:depth:post-approval` (§5), `bt:<id>:phase:failed:<phase>` (§4.6), `bt:<id>:phase:blocked:<phase>` (§4.1, a worker-reported block), `bt:<id>:impl:harness-touched` (§8.3), `bt:<id>:chain:receipt-rejected:<repo_id>:<seq>` (§8.5; the rejected receipt is the identity), `bt:<id>:verdict:stale` (§8.6), `bt:<id>:guardian:dead` (§8.6), `bt:<id>:merge:refused` (§9.5), `bt:unknown:merge:unbound:<repo_id>:<pr>` (§9.2; the PR is the identity, one escalation per unbound PR, never a collapsed count), `bt:<id>:intake:ownership-lost` (§2.5, §9.3 B6), `bt:unknown:intake:orphan-claim` (§2.4.7), `bt:<id>:infeasible` (§3.1), `bt:<id>:lease:starved` (§10.2), `bt:<id>:lease:conflict` (§10.2), `bt:<id>:impl:over-budget` (§8.2), `bt:<id>:cancel:draining` (§3.5), `builder:app-install:<repo>` (§7.1, §9.3 U4), `builder:sandbox:canary-failed` (§4.4), `builder:backup:failed` (§11.4), `builder:probe:merged` (§9.1, a P0 incident that also writes the HALT marker).

**Escalation ownership is by process.** Builder escalations (`^bt:` and `^builder:`) live in the hub's **own** `escalation` table (§11.2) and are raised and retired only by the builder process, with the hub task state as their retirement witness (never `gh pr view`). Guardian escalations stay in the per-repo store and are raised and retired only by the guardian daemon that owns it; the guardian never writes a builder identity and the builder never writes a guardian one. `announceable`'s subject-grammar dispatch runs **in the process that owns the store it reads**: the builder's `announceable` reads hub escalations and dispatches `^bt:` and `^builder:` subjects; each guardian's `announceable` reads its own store with the guardian grammar unchanged. No process announces from another process's table (§13). Every alert names the single founder action needed.

## 15. Resolved contradictions (which source lost, and why)

1. **Research gate at claim**: judged factual, not stylistic; S5 resolves it empirically against a copy of the live ledger; the conforming no-force path is preferred if it does not self-block. The losing posture was picking a side without measuring.
2. **`reviewArtifact` shape**: the optional `gate` parameter lost to the sibling function: an optional safety parameter is the exact failure class that bit four times in one day; a separate mandatory function removes the class instead of asserting around it. The same ruling governs resume dispatch (§4.8): the settings parameter hard-fails rather than defaulting.
3. **Where the merge actuator lives and when it gains authority**: "guardian executor, dark behind profile authority" lost twice. The live profile already sets `propose_and_merge`, so it was never dark; and a guardian-owned merge intent could not see a hub cancellation in the same transaction. The coordinator is hub-owned and builder-only (§9), lands dark at S8 behind an independent default-false switch plus a process flag, soaks through S9, and gains authority at S10. Code early, capability last, with a switch that is actually off.
4. **`--fast` gate skip**: lost. Pre-authorization at filing binds to no head SHA; no size or flag skips the gate; trivial tasks get short specs, not no specs.
5. **Terminal state for lost claim races**: explicit **LOST** won: quiet, terminal, no alarm, durable, visible in dash. LOST appends nothing to the ledger (§2.4.6).
6. **Per-phase model and effort**: per-action knobs won, with the resolved model id snapshotted per run (§4.7) so an alias cannot drift under a retry.
7. **Ownership re-check cadence**: every-transition re-verify won; the full-sync list covers every externally visible transition, IMPL_PR_OPEN, resume, and the merge pre-flight included (§2.5).
8. **Gate timers**: the synthesis's 30-minute founder window and its founder-first table are superseded by the founder's 2026-08-21 revision (§7.3): Codex clean is a mandatory serial witness, and the founder window is 15 minutes. The audit's refinement (measure from the delivered notice, not from Codex's timestamp alone) was adopted because it changes nothing in the normal case and closes a real hole in the abnormal one.
9. **Cross-store writes**: "one narrow witnessed guardian-to-hub write" lost to "one owner plus an idempotent import" (§1.3, §8.5). SQLite cannot commit two files atomically under WAL; the narrowness of the write did not change that.
10. **Quota by observation**: the builder-written quota ledger lost to a transactional provider scheduler both daemons claim (§10.4). Preserving "zero guardian hub writes" mattered less than enforcing the promised guardian priority; the exception is exactly one table pair.
11. **OS file locking**: removed everywhere. The primitive is absent on the host and Node has no binding (Appendix B, P0-5); the singleton lease row, the `wx` clone lock, and remote optimistic verification replace it (§1.2, §2.3).
12. **Ten files**: a universal invariant lost to a weighted default budget with a founder-approved atomicity exception (§8.2). File count is a proxy; an atomic schema-plus-migration change that cannot split is not made safer by being split.

## 16. Open questions, and defaults chosen

### 16.1 Defaults chosen; founder may override

These are the audit's recommendations adopted as this design's defaults. Each is in force unless the founder overrides it in writing in the tracker.

1. **Human/code-owner approval on implementation PRs is retained during the pilot** ("supervised autonomy", §9.1). Removal is a later decision, after server enforcement is live and canary evidence exists.
2. **No ordinary-PR auto-merge in this programme** (§9.1, §9.2). It is a separate design and authorization.
3. **Codex unavailable**: closed by founder ruling (2026-08-21, "if Codex is not available, human approval will be enough"): no waiver flag exists; the founder's ordinary SHA-bound approval advances a spec whose head Codex has refused or left unanswered within the response window (§7.3 row 7). Founder silence never advances without a clean pass.
4. **Ten files is a default, not a ceiling** (§8.2): weighted budget, package limit, founder-approved atomicity exception.
5. **The guardian may write the global provider scheduler**, and nothing else in the hub (§10.4, §13).

### 16.2 Open questions (what the measurements could not settle)

1. **Does Codex review on private repos at all?** Installed with selection=all, but zero reviews exist on any private revnix or nextly-ops PR ever. The first S4 spec PR is the measurement; `reeve builder doctor` reports the current answer. A Codex-dead spec repo is not a halted builder: after the response window the founder's approval alone advances each spec (§7.3 row 7), so the measurement decides only how often that path is taken, never whether work can proceed.
2. **Off-device encrypted backup destination** (§11.4). The requirement is fixed; the destination is the founder's call. By the Platforms ruling the destination is **local only**: a second machine on the LAN, a NAS, or an external disk (never a cloud service and never a GitHub repository). Which of those, and its retention, is the founder's call. Until decided, same-disk snapshots run and doctor reports the off-device copy as missing.
3. **Does the research-node-first claim protocol self-block?** Resolved empirically in S5 (§2.4.8); both protocols are specified.
4. **Headless-versus-interactive subscription pool.** The CLI documentation (verified 2026-08-21) states that headless usage draws from the same seat allowance as interactive usage and names no separate pool; S3 measures the actual rate window anyway, and the provider limits follow the measurement rather than the documentation (§10.4).
5. **Second-project onboarding.** revnix repos need a fresh App installation (founder action); rext and 21century have no ledger, so intake there is founder-filing only. The registry and per-project specRepo fields are ready; nothing else is assumed.
6. **The guardian's serial-dispatch defect** remains: a long FIX_CI blinds verdict publishing for that repo. The builder does not inherit it, and the provider scheduler plus fast-fail cap its worst case, but fixing the guardian loop is its own future programme.
7. **IMPLEMENT budgets (60-90 min) are guesses.** Calibrate from S3 and S6; the knobs are per-action profile fields, so tuning is config, not code.
8. **Does `gh.review.request` alone trigger Codex on nextly-ops, or is the trigger comment required?** Both are posted (standing rule), so the answer is observable without being load-bearing.
9. **Ledger long-term store.** The ledger's own plan (SQLite WAL store, salvaged spike passing 29/29) is the successor to JSONL plus the typed CLI. Who migrates human lanes onto it, and when, is a founder decision outside this programme; the §2.3 hardening is designed to be compatible with either store.
10. **`--bare` for workers.** Adopt only once subscription authentication under bare mode is proven on the installed CLI (Appendix B, N1); until then `--safe-mode` plus explicit settings is the boundary.
