### The CI discriminator — use v3, not the old one

The instrument in the old tick prompt (`jobs_with_steps == 0`) is **one step short** and
took three revisions this session. Zero steps has **four** readings, not two:

```
dead    = jobs with status=completed AND conclusion NOT IN (skipped,cancelled) AND steps == 0
ran     = jobs with steps > 0
pending = jobs with status != completed

dead > 0     -> OUTAGE: nothing ran; the conclusion says nothing about the code
ran  > 0     -> REAL RESULT: read the diff
pending > 0  -> says nothing YET
otherwise    -> all skipped: says nothing
```

A legitimately **skipped** job has zero steps. So does a job that has **not finished**.
v2 of this discriminator declared an outage in a repo a peer had just measured healthy —
the disagreement was the instrument. Verified against three repos with known-different
answers.

**Replace with reeve's own gates:**

- **The four-check stub loop** on every fix: control green → stub verified applied → the
  RIGHT assertion red → restore byte-identical **by file copy, never `git checkout`**.
  *A stub that produces no failures means the property is untested.*
- **Verify a merge by CONTENT, never ancestry** — this repo squash-merges, so branch
  commits are never ancestors of `main`. Compare tree hashes or file blobs.
- **Never merge without an explicit per-PR grant.** Grants never carry over.
- **Run the full suite under both timezones** while CI is out; measure every pass against
  **one base**, never a chained comparison.
- **Never truncate a search you will reason about as a set.** Print the count first. Every
  absence claim needs a positive control.
- **The peer-lane territory protocol** — tell the other lane before touching
  `src/daemon.mjs`, `src/db/**`, `src/outbox/**`, `src/github/**`, `src/pr.mjs`,
  `src/verdict.mjs`, `src/watcher.mjs`, `src/review/**`, `src/prompts.mjs`; and always
  before changing the SHAPE of `computeVerdict`'s clause set or the ORDER of `nextAction`'s
  branches.
- **Do not** restart the reeve daemon, run `launchctl`, run `reeve canary`, or `git pull`
  in `~/Work/Products/reeve` — a live guardian runs from that checkout. `git fetch` is fine.
- **Never `git stash`** — the stack is shared across ~19 worktrees.

### The claim protocol the founder asked for — multiple lanes are confirmed

- **Claim before starting.** Nothing is worked unclaimed.
- **One task at a time.** Finish, verify, merge, then claim the next.
- **Read the tracker first** — see what other lanes hold; do not touch their files.
- **Update after each task, not in a batch** — status, PR, findings, decisions.
- **"Done" means merged and verified by content**, never "PR opened". This has already
  bitten: `docs/TRACKER.md` has **10 of 20 unchecked boxes sitting on merged work**, two
  reading "PR open" for PRs that merged the day before, because the tracker is edited by
  the PR that builds the work and never again after the merge.
- **Release a claim you abandon.** A stale claim blocks another lane exactly like a stale
  provider lease — a defect reeve itself fixed this week.

**Mechanism, decided:** **one small file per claim** under `trackers/claims/`, named for
the task. Two lanes claiming different tasks never touch the same file, so claims never
conflict, and a claim is visible on `main` the moment it is pushed. This mirrors reeve's
own lease model.
