## 2. WHAT TO DO FIRST — #69's three findings

All three are one shape: **a field in the characterisation signature that looks populated but
cannot detect the change it exists for.** Full text is on the PR; the substance is here so it need
not be re-read.

1. **`10-maintenance-on-release-and-cooldown` never reaches the cooldown half.** Only
   `providerRelease` sees `maintenance`; `noteCooldownWithRetry()` is never called, the artifact
   contains no `noteRateLimit` seam call, and `cooldownRetry` stays empty. **The scenario's NAME
   promises coverage it does not have.** Fix: make the worker result rate-limited and have
   `noteRateLimit` refuse with `reason: "maintenance"`.

2. **`id` is over-redacted.** The harness builds a fresh fixture per run and the claim
   deterministically returns id `1`, so the release's id is **behavioural data, not host noise**.
   Redacting it means a refactor that releases id 2 instead of the claimed id 1 compares equal —
   and the lease suite only checks owner/repo/runRef, so it would not catch it either.

3. **The default claim returns no token**, so every release records `"token":null`. The token is
   the fence that stops a delayed pre-restore release deleting a newly reused lease. Dropping the
   token from the release path would be invisible. Fix: return a deterministic token from the
   default claim and require the same token on release.

**Then:** full suite, reply **and** resolve each thread via GraphQL, `@codex review`.

### The design decision that matters most, and it changed twice this session

The issue's own text says: *"adding a new call site must not be able to skip a rule. If that
cannot be expressed, the design is not finished."*

**The acceptance test is a PROVENANCE assertion, not an unreachability assertion.** Recorded as a
comment on issue #50. The reasoning, because it will be re-derived otherwise:

- Asserting "the raw handle is unreachable" passes for three different reasons — a `TypeError`
  from a missing argument, an unrelated validation throw, or genuine unreachability. Only one is
  the property.
- Pairing it with a positive control proves the *operation* works, which is **a different claim
  from the one at risk**.
- **An unreachability assertion has no natural positive control.** A provenance assertion does:

```js
acquisitions.length > 0                    // vacuity: the tick really did acquire handles
acquisitions.every(a => a.via === session)  // property: every one came through the session
```

No arrangement leaves both green while the property is false. It also survives a **rename, a
re-export, or the handle arriving as a parameter** — the three ordinary things that defeat a
name-grep.

**A grep is the same unverified-claim shape one level down.** `!/\bopenHub\b/` asserts *"this name
does not appear"*; the claim needed is *"this authority is not reachable"*.

**If the provenance assertion cannot be expressed against the real tick, that is a RESULT and gets
reported** — not a weaker test shipped as done. The expressibility check moves to the front.

## 5. The findings that matter beyond their fix

**The instrument measured something adjacent to the property — four coats, one week.** The peer
lane's phrasing, and the most useful generalisation to come out of this session: *the adjacent
thing gets chosen because it is easier to get at.* Instances: a marker file written inside the
tree whose cleanliness was under test; a line count treating a two-character overhang as a line; a
name-grep standing in for reachability; an exit code standing in for an assertion.

**A stale-but-true value reads as corroboration.** `verify-merge.mjs` was asked to name the
verified head. Implemented naively it would print `headRefOid`, which **GitHub freezes at merge
time** — for `reeve#63` it still reports `9232d4a` while the branch stands at `4e5df36`. Printing
it would be **worse than printing nothing**. The live tip is read separately, four states: `read`,
`gone` (UNKNOWN, not reassurance), `unreadable`, and omitted (silence). **The founder's
rebase-merge setting change does not help here** and the verifier does not read it.

**Never implement a proposed fix without testing it against the case that prompted it.** The above
is why. Having the question and checking the answer are separate disciplines.

**A snippet in a Markdown fence ships unrun**, and its failure modes almost all turn a FAILED read
into a PASS: an unchained `git fetch` reading a cached ref; `|| echo` turning a failed guard into
success; `for p in $(git … -z)` word-splitting into fragments that compare equal; two unchecked
`ls-tree` substitutions where `""` equals `""`. One printed `MERGED, AND INTACT ON MAIN` on an
**unmerged** PR. **Extract every fenced command block and RUN it before committing.**

**`grep -c '^FAIL'` returns 0 on a crashed run.** Judge on **exit code** and the `all green` tail,
never a FAIL count. Hit twice this session, once where every assertion printed PASS and the
process then exited 1 on a double-close.

**Determinism is not portability.** The characterisation check runs a scenario twice in one
process. It proved reproducibility and could not see that artifacts embedded the host's Node
interpreter path — six scenarios failed in CI with no behaviour change.

**"Derived" is not one property.** The seam list was derived from `ctx` and that was still the
wrong source: `tick()` resolves seams as `(ctx.NAME ?? fallback)`, so a seam absent from `ctx`
runs the production fallback **unrecorded**. Derive from what the **daemon consults**.
