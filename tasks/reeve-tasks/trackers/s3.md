## 5. The durable findings

The lessons, not the changes. These are about plans and designs being wrong, so they cannot
live inside a plan.

**The durable finding is that a plan can survive sixteen adversarial review rounds and still
contain a test that cannot fail.** It was found by *executing* Task 1, not by reviewing it. A
review reads for what is wrong; only a run reads for what is absent. Every S3 task therefore
names its stub as a **step**, not as a promise in the preamble — S2-B promised *"every task
names the stub explicitly"* and then contained the word `stub` exactly once, in that very
bullet.

**The durable finding is that an enumeration reports itself complete.** A hand-built list of
side effects, call sites or cases returns the items the author thought of, and nothing in the
output says the list is partial. On reeve#44, a four-item list of what a halted guardian would
newly execute was published as three; the peer lane read the same span and found the fourth.
Say what you searched and how, so the boundary travels with the claim.

**The durable finding is that absent and unreadable are different facts, and treating them as
one is this repository's dominant defect class.** A skipped CI job and a CI job that never ran
both report zero steps. An empty branch list and an unconfigured watcher both report nothing.
The instrument that cannot tell them apart answers a smaller question and reports success.

**The durable finding is that a mechanism's limit does not travel with the mechanism.** Carry
contracts between stages, never tuned numbers: an inherited workaround constant hides a real
defect behind a green run.

**The pattern worth keeping.** Twenty-four disagreements across six documents, and **not one was
found by reading the brief** — every one came from opening the file the brief cited. The brief
was itself the product of a fourteen-agent audit that measured carefully; it went stale in two
ways at once, by a merge (D3, D13) and by an assumption that a declaration implies an
implementation (**D1, D2, D5, D6** — four instances of the same shape in one stage). That shape
already has a name here: *permission to read is not a reader*, and *a comment describing a
mechanism is not the mechanism*. **D1, D2, D5, D6, D19 and D20 are six instances of it in one
stage** — a declared writer with no writer, twice; a minter named in a comment and never
written; a column in an INSERT's table but not in its column list; and a subcommand that
`doctor` advises and `bin/reeve` refuses. **After the third instance of one shape the design is
wrong, not the instances** (`../MASTER-PLAN.md` §B.11's W2 is the structural version): the
cross-check at `test/hub-crosscheck.test.mjs` can prove a writer *claim* was made and can never
prove the writer exists, and that is the gap all six fall through.

### The one that needs a founder decision

**D1.** `reeve task file --depth deep` would be accepted, validated against the closed depth
set, and then **thrown away**, because `admitTask` has no column for it in its INSERT. The task
would file at whatever depth SIZING later computes, and the founder's stated depth would have
had no effect — **a flag that reads as working**. Design §5 does give the founder a depth
override, so dropping the flag is not obviously right either. The choice is to widen
`admitTask`'s INSERT (two columns, inside S3-B's territory, with a migration only if the
columns are absent from `hub.sql` as well as from the INSERT) or to ship T3 without the two
flags and add them when the override path lands. **This is recorded here and not decided.**
